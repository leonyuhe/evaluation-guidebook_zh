模型评测究竟在评什么？

当你穿行于 LLM 的世界——无论你是在训练或微调自己的模型、为你的应用挑选一个模型，还是想弄懂这个领域的现状——有一个问题你很可能已经撞见过：

怎样才能知道一个模型是否好？

答案是（考虑到本博客的主题，这其实并不令人意外）评测！它无处不在：给模型排名的排行榜、声称能衡量推理、知识、编码能力或数学表现的基准、宣布新 SOTA 结果的论文……

但评测究竟是什么？它究竟能告诉你什么？

本指南就是来帮你把这些都搞清楚的：评测能做什么、不能做什么，什么时候该信任不同的方法（以及它们各自的局限和偏见又是什么！），评测一个模型时如何挑选基准（以及 2025 年哪些基准仍然相关），还有——如果你愿意的话——如何设计你自己的评测。

在整本指南中，我们还会重点指出常见的陷阱，以及 Open Evals 团队的经验与技巧，并希望能帮你学会批判性地看待那些从评测结果中得出的论断。

本指南聚焦于语言（主要是自然语言）的评测，但许多原则同样适用于其他模态

在深入细节之前，我们先快速看看人们为什么要做评测，因为你的身份和你正在做的事，会决定你需要使用哪些评测。

模型构建者的视角：我在构建一个强大的模型吗？

如果你是正在创建一个新模型的研究者或工程师，你的目标很可能是构建一个在一组任务上表现良好的强大模型。对于基座模型（从零开始训练），你希望模型在一系列通用任务上表现良好，这些任务衡量各种不同的能力。如果你是在为某个特定用例后训练一个基座模型，你大概更关心模型在那个特定任务上的表现。无论哪种情况，你衡量表现的方式都是通过评测。

当你尝试不同的架构、数据配比和训练配方时，你要确保自己的改动（选择不同的训练数据、架构、参数等）没有“破坏”具备这些属性的模型应有的表现，甚至可能还提升了它。测试不同设计选择所带来的影响，靠的是消融实验：消融实验是一种实验，你通常会在某种特定设置下训练一个模型，在你选定的任务集上评测它，再把结果与基线模型比较。 因此，评测任务的选择对消融实验至关重要，因为它决定了你在构建模型的过程中会朝着什么方向优化。

对于基座模型，人们通常会选择其他模型构建者使用的标准基准任务（想想新模型发布时总会报告的那份经典基准清单——我们会在下文过一遍）。对于特定用例，你可以使用现成的评测任务（如果有的话）——如果它们算不上“标准”，你多半得好好审视一番——也可以自己设计（下文会讨论）。由于你可能会跑大量消融实验，你会希望评测任务能提供足够强的信号（而不只是毫无意义的噪声结果），同时希望它们跑得便宜、跑得快，这样你就能快速迭代。 通过消融实验，我们还能借助缩放定律，根据较小模型的表现来预测更大模型的表现。

除了为实验做消融，你很可能还想在模型训练过程中对中间检查点做评测，以确保它确实在学习、在不同任务上不断进步，而不会因为尖峰或其他问题开始退化。最后，你还要评测最终的检查点，这样在发布时才能宣布自己的模型达到了 SOTA。

小提醒

尽管各种宣称往往很宏大，但对于任何复杂能力，我们目前都无法直接说“这个模型在这方面最好”，而应该说**“这个模型在这个特定任务的这些样本上最好，我们希望这些样本能很好地代表这项能力，但没有任何保证”**。

（你仍然可以宣称自己是 SOTA，只要把这条保留意见记在心里。）

模型使用者的视角：哪个模型在某个任务上最好？

你想用别人训练好的模型来满足自己的特定用例，而不做额外的训练；或者你打算做额外的训练，正在寻找最好的现有模型作为基础。

对于数学、代码或知识这类常见主题，通常会有多个排行榜用不同的数据集对模型进行比较和排名，你一般只需测试排名最靠前的几个候选，就能找到适合自己的最佳模型（如果它们都不合用，排在后面的模型多半也不合用）。

你可能还想自己跑评测和比较（复用现有基准），以获得更多细节来分析模型成功与失败之处，这一点我们会在下文介绍。

在他们的论文中，作者总结了 ImageNet 时代在基准测试与数据集设计上的经验教训，他们主张：既然分数容易不稳定，那么评估模型唯一稳健的方式就是通过排名，更具体地说，是找到能提供一致且稳定排名的大类评测。我认为寻找排名的稳定性确实是一种极有意思的模型基准测试思路，因为我们已经展示过：LLM 在自动化基准上的分数极易受提示的细微变化影响，而人工评测也并没有更一致——在使用稳健的评测方法时，排名实际上更稳定。

与模型构建者为某一特定能力做爬山式优化类似，对于不那么常见的主题，你可能需要设计自己的评测，这在最后一节有详细说明。

那衡量 AGI 呢？

对于机器学习模型的智能究竟是什么、以及如何评测它，我们严重缺乏好的定义和框架（不过确实有人尝试过，例如 2019 年的 Chollet，以及今年的 Hendrycks 等人）。难以定义智能并不是机器学习特有的问题！在人类和动物研究中，智能同样很难定义，而那些试图给出精确分数的指标（例如 IQ 和 EQ）也饱受激烈争论与争议，而且这种争议是有道理的。

不过，把智能当作目标本身存在几个问题。1）智能往往会变成移动的靶子：每当我们达成一种曾被认为是人类独有的能力时，就会重新定义这个词。2）我们当前的框架是以人类（或动物）为出发点构建的，很可能无法很好地迁移到模型上，因为底层的行为和假设并不相同。3）它其实也是个没什么用的目标——我们应该以让模型做好具体的、定义清晰的、有目的且有用的任务（想想会计、报告等）为目标，而不是为了 AGI 而追求 AGI。

理解评测所需的 LLM 基础知识

现在你已经了解为什么评测对不同的人都很重要，接下来看看我们如何通过提示模型得到一些答案，以便对它们进行评测。如果你已经做过评测，可以略读这一节，主要留意注释和旁注。

在本节中，我们来看模型的两个步骤：输入如何经过预处理后交给模型（tokenization），以及模型如何据此生成预测（inference）。

分词

输入文本（在推理时称为提示词）首先被切分成 token，即文本的小单位（可以是一个或多个字符，最大到词级别），每个 token 都关联一个数字。模型能解析的 token 全范围称为它的词表。

分词基础：我们为什么要分词，又如何分词？

因为大语言模型实际上就是大型数学函数，它们吃的是数字，不是文本。

假设你想把一句话转换成数字。你首先需要决定如何把句子切成小块，然后把每个小块映射到一个数字；这就是分词。

过去，人们会尝试把文本的每个字符映射到它在字母表中的索引（a -> 1、b -> 2 等），这称为基于字符的分词（在字符之间切分）。在光谱的另一端，人们也尝试把每个词映射到它在词典中的索引（a -> 1、aardvark -> 2、ab -> 3 等），这称为基于词的分词（按空格切分——前提是你的语言有空格；如果没有，就会稍微麻烦一些）。

这两种方法都有一个很强的局限：它们会从输入文本中移除信息。它们抹掉了你能从词形上看出的语义联系（例如 dis similar、similar、similar ity、similar ly），而这些正是我们希望模型保留的信息，好让它把相关的词联系起来。 （另外，如果输入里突然出现一个全新的词会怎样？它拿不到数字，你的模型就没法处理它 😔 ）

因此有人想到把词切成子词，并给这些子词分配索引（dis、similar、ity、ly）！

最初这是用形态句法规则完成的（形态句法有点像构词的语法）。现在大多数人使用字节对编码（BPE），这是一种聪明的统计方法，根据子词在参考文本中的频率自动生成子词。

所以总结一下：分词是一种把文本的小单位（可以是一个或多个字符，最大到词级别）映射到数字（类似索引）的方式。当你想处理文本时，你的输入文本（在推理时称为提示词）会被分词器切分成这些 token。模型或分词器能解析的 token 全范围称为它的词表。

管理微调模型、系统提示词和对话模板

2022 年之前，模型通常只是预训练：输入文本，输出文本，没有别的。然后，2023 年我们有了指令微调和对话模型，2025 年又有了推理模型。这意味着我们从使用原始文本，转向使用越来越多的格式。

这意味着如果你不确保做到以下几点，不少模型的表现会很糟：

  1. 遵守模型期望的格式
  2. 如果你的模型需要系统提示词，在推理的最开始添加一个
  3. 在处理推理模型的答案之前，先移除其中的思考轨迹（通常可以用正则去掉 <think> 标签之间的内容）

注意句子起始和结束 token

一些预训练模型（比如 Gemma 系列）在推理时对是否包含句子起始 token极其敏感。你可能需要做几个实验，看看你的情况是否也会如此；如果这些 token 不在你的数据集里，评测时就要手动加上。

你可能还会遇到这样的问题：模型不会像你预期的那样在句尾 token 处停下来。代码模型通常是以 \n\t 作为单个 token 训练的。这意味着在生成文本时，它们常常会一步就生成 \n\t。如果一个任务把 \n 定义为句尾 token（= 停止生成），那么当 \n\t 被预测为单个 token 时，模型就会在它之后继续生成，因为它与 \n 并不相同。但你实际上仍然希望模型停下来。在这些情况下，你要么需要更新句尾 token，要么定义一个机制，回溯最近这些 token 的字符表示，从而在事后停止（并截断）生成。

多语言性与分词

在看多语言评测时，你会遇到两个问题。

第一，由于有些语言并不总是用空格作为词的分隔符（仅举几例：韩语、泰语、日语、中文），它们需要特定语言的分词器才能被正确切分，否则会影响它们在 BLEU、F1 分数等指标上的得分。

其次，分词器整体上可能对非英语语言不公平。训练 BPE 分词器时，你会使用想要覆盖的各语言的数据，但大多数时候，这些数据在语言之间是不平衡的（例如，英语数据比泰语或缅甸语多出一个数量级）。由于 BPE 分词器根据出现频率最高的词来构建词表 token，大多数长 token 都会是英语单词——而来自使用频率较低的语言的大多数词只会在字符级别被切分。这一效应导致多语言分词中的不公平：某些（频率较低，或资源较少的）语言需要多出几个数量级的 token，才能生成与英语等长的句子。

如果你处于这种情况，那么评测中允许模型生成的 token 数也应当取决于语言，因为并非所有语言都会被分词成相近数量的 token。

推理

现在我们知道了如何把输入文本转换成 LLM 能解析的形式，接下来看看模型如何处理这段文本。

基于这段输入文本，LLM 会在整个词表上生成下一个最可能 token 的概率分布。要得到连续的生成结果，我们可以取概率最高的 token（再加上一些随机性，让输出更有意思，具体多少视情况而定）作为下一个 token，然后重复这一操作，把新 token 当作提示词的结尾，依此类推。

🎯
两种主要评测方法

对数似然评测：给定一个提示词和一个（或若干个）答案，我的模型给出该答案的概率是多少？

生成式评测：给定一个提示词，我的模型会生成什么文本？

选择取决于你的任务（如下文所述）以及你的模型：API 背后的大多数模型不返回对数概率，因此你需要系统地使用生成式评测来评测它们。

对数似然评测

对于对数似然评测，我们想要的是在给定提示词时一个或若干个选项的条件概率——换句话说，给定一个输入，得到某个特定后续内容的可能性有多大？ 那么：

  • 我们把每个选项与提示词拼接起来，送入 LLM，它会根据前面的 token 输出每个 token 的 logits
  • 我们只保留最后的 logits（与选项 token 相关联的那些），并应用 log softmax 得到对数概率（取值范围是 [-inf, 0] 而不是 [0-1]）
  • 然后我们把各个 token 的对数概率求和，得到整个选项的对数概率
  • 最后我们可以基于选项长度做一次归一化

这让我们可以应用以下指标之一：

  • 得到模型在若干选项中的偏好答案，如上图所示。（然而，这可能让那些本来会自由生成其他内容的模型占便宜，比如图中的 Zygote。）
  • 检验单个选项的概率是否高于 0.5
  • 研究模型校准。一个校准良好的模型，是指正确答案具有最高概率的模型。

要进一步了解校准，你可以看 Anthropic 的这篇论文，它讲了校准是什么、如何检测，以及如何训练模型使其校准良好；还可以看这篇论文，它讨论了校准的一些可能局限）。

一道多项选择题的答案也可以用自由形式的生成式评测来表达！因此，你有时会看到对任务形式（formulation）的提法。

有三种常见任务形式：

  • 多项选择格式（MCF）：我们比较各选项索引的似然，选项在提示词中显式给出，并以 A/B/C/D 为前缀（如 MMLU 中那样）
  • 完形填空形式（CF）：我们比较不同选项的似然，但不把它们提供在提示词中
  • 自由形式生成（FG）：我们评测给定提示词下贪心生成的准确性

FG 需要大量潜在知识，在短期的预训练消融实验中通常对模型来说太难。因此，在运行小规模消融实验时，我们通常聚焦于多项选择形式（MCF 或 CF）。不过，对于后训练模型，FG 成为主要形式，因为我们要评测的正是模型能否真正生成有用的回答。 不过，研究也表明，模型在训练早期难以应对 MCF，只有在大量训练之后才学会这项技能，因此 CF 能提供更好的早期信号。所以我们建议在小规模消融中使用 CF，并在主实验中纳入 MCF，因为一旦模型越过某个阈值、为 MCF 带来足够高的信噪比，MCF 就能提供更好的训练中期信号。 再补充一点：在 CF 这类序列似然评测中，为了给模型的答案打分，我们把准确率计算为“正确答案具有最高的、按字符/token 数归一化后的对数概率”的问题所占的百分比。这种归一化可以防止对较短答案的偏好。

MMLU MCF 变为非随机表现的时点取决于模型规模和训练数据。对于 7B 的 transformer，OLMES 论文发现模型在 500B token 之后才开始表现出非随机的性能。对于 1.7B 模型，我们在 SmolLM2 中发现这发生在 6T token 之后。

是否应该始终把上下文和选项一起分词？

在多项选择 MCQA 评测中，通常你会希望把上下文和选项一起分词，因为这样生成的 token 序列对模型来说更可能、也更自然。

然而，有些分词器（例如 Llama 的那个）并不满足 tok(context + choice) = tok(context) + tok(choice)（它们会增删空格）。这意味着只比较各选项的对数概率并不简单，因为上下文的 token 可能“渗出”到选项里，把比较搞乱。

举个具体的例子，假设你的词表基础 token 是字符 C1、C2、C3，而 C1C2 恰好也是 BPE 过程中学到的一个单独 token。

假设你的上下文是 C1，选项是 C2 和 C3。 如果你把上下文和选项一起分词，你比较的是 C1C2（一个 token）与 C1+C3（两个 token）。即使你按长度对对数概率做归一化，你比较的也不是同一个东西。 而先分别对上下文和选项分词再比较，意味着你比较的是 C1+C2 与 C1+C3。但既然 C1C2 是一个 token，C1+C2 在你的编码器所见过的那类数据中大概很罕见，因此对模型来说这是一个不太可能的连续序列，这会扰乱你的对数概率。

如果你的模型是这种情况，解决方案通常是选择“最不坏”的那个选项，比较可比较的东西：分别计算上下文和选项的 token，然后在移除可能被添加的特殊句首/句尾 token 之后把它们拼接起来。

生成式评测

在生成式评测中，我们要的是模型在给定输入提示词时生成的文本。

它是通过自回归方式得到的：我们把提示词传给模型，查看最可能的下一个 token，把它选为模型“生成的第一个 token”，然后重复，直到达到某个结束生成的条件（最大长度、用于停止生成的特定 token 等）。模型生成的所有 token 都被视为它对提示词的答案。

然后我们可以把这次生成与参考文本进行比较，并对两者之间的距离打分（使用精确匹配这类简单指标、BLEU 这类更复杂的指标，或者以模型作为裁判）。

用现有基准进行评测

现在你已经（重新）熟悉了分词与推理如何运作的必要基础知识，也了解了做评测时有哪些注意事项，让我们来看看实际的基准评测！我们会先简要浏览 2025 年的各类评测，然后讨论在看一个基准时该关注什么，以及为什么你很可能无法复现公布出来的分数。最后，我们会和 FineWeb 团队一起讨论一个特殊情况：如何挑选好的基准来评测训练。

⚠️
重要概念

在这一节中，你会经常看到两个概念：数据污染和饱和。

饱和是指模型在某个基准上的表现超过了人类表现。更一般地说，这个词用于那些不再被认为有用的数据集，因为它们已经失去了区分不同模型的能力。

这正是你在横幅图片中看到的现象！

如果你的评测中所有模型都接近可能的最高分，那它就不再是一个有区分度的基准了。这类似于用幼儿园的题目考高中生：成功说明不了什么（尽管失败很有指示性）。

数据污染是指评测数据集最终进入了模型的训练数据集，在这种情况下，模型的表现被人为抬高，并不能反映其在任务上的真实世界表现。

这有点像用学生已经提前知道答案的问题来考学生。

2025 年需要了解的基准

你可以单独评测特定能力——在训练过程中获得信号，或者在比较基座模型/预训练模型时，这通常很有意思。（不过，如果你用以下评测来挑选和验证训练方法，那么在最终模型上报告这些评测结果会略有偏差，因为你的训练方法已经被你朝着在这些评测上取得好成绩的方向调整过了）。

如果你对评测还不太熟悉，可以随意略读这一节，等你需要为某个具体能力寻找数据集时再回来看看 :)

推理与常识

推理与常识数据集往往是“历史”数据集，构建于 BERT 和嵌入模型的时代、LLM 热潮之前。它们在当时相当有挑战性（尤其因为它们常常是针对当时的模型对抗性地构建的），但如今它们 1）太简单 2）已被污染/饱和，只应被用于消融实验或作为预训练评测。较大的数据集有时也包含错误或低质量问题，因为它们往往是通过 Amazon Mechanical Turk 构建的，以便快速、低成本地扩大规模（而如今这件事改由用 LLM 生成评测问题来完成）。

ARC（2018）（不要和 ARC-AGI 混淆）是一个基于人类测试构建的小学科学 MCQA 数据集。选项是针对当时的词共现系统对抗性地挑选的。它有几个子集，质量更高的 challenge 子集至今仍用于预训练。WinoGrande（2019）是一个众包（mechanical turk + 验证）的代词消解/填空数据集，使用对抗性的成对条目来骗过模型。这两个数据集对模型来说都相当难，直到 2022 到 2023 年才被攻克。

不少历史数据集专门考察需要某种常识理解、并能与现实世界对应的推理。HellaSwag（2019）要求 LLM 在一组对抗性选项中选出正确的下一句，文本来自 ActivityNet 的说明文字和 Wikihow 的教程。（它是一个名为 Swag 的数据集的后续）。由于大多数句子来自教程或活动描述，它们往往需要物理常识的支撑才能解决。同样地，CommonsenseQA（2018）是一个基于 ConceptNet 构建的常识 MCQA 数据集——标注者编写问题，然后用概念上接近的干扰项作为选项。PIQA（2019）专门考察物理常识问题（由 Instructables.com 上的示例创建，其选项同样是通过语义扰动或改写得到的对抗性选项）。OpenBookQA（2018）提供开卷事实来帮助回答 MCQA 问题——然而，这些问题还需要潜在的常识知识。

一个更新的、很酷的推理数据集是 Zebra Logic，它用逻辑谜题来测试模型的推理能力。他们的方法可以无限生成谜题，因此污染很少。

知识

知识领域最主要的评测数据集一直是 MMLU（2020）。它已进入饱和/污染状态，经过更深入的检查后，人们发现了若干问题：引用了不存在文档的不完整题目、错误的标准答案、有歧义的题目，以及所选主题中露骨的美国中心主义。因此它在 MMLU-Redux（2024）中得到了清洗，在 MMLU-Pro（2024，目前社区使用的主要替代品）中用更复杂的题目和更多答案进行了扩展，并针对文化偏见在 Global-MMLU（2024）中做了翻译与标注。这些主要用于预训练评测和消融实验。

对于后训练，人们会关注更难、更高质量的知识数据集。GPQA（2023）是生物学/化学/物理学领域的博士水平定制题目，其设计目标是让正确领域的博士生能够回答，而其他人不行。最常用的子集是 diamond 子集，但自 2023 年发布以来，它也开始出现污染。

最后但同样重要的是，名字起得颇为浮夸、质量却非常高的 Humanity’s Last Exam（2024）收录了 2.5K 道由各领域专家众包提供的问题，横跨多个领域。它大体上是不公开的，题目既需要复杂的知识，也需要推理。它至今仍未被攻破，在我看来是个很酷的数据集。唯一的问题是，由于没有办法快速给模型打分，如今人们改用 LLM 裁判来评估模型的答案，而不是对照标准答案来检查，所以它属于那种在真实使用中会得到完全不可比结果的评测。

不过，尽管在几年前测试模型潜在知识的原始质量非常合理（在训练过程中检验模型质量时也仍然有意思：预训练阶段用 MMLU-Pro 这类评测，后训练阶段用 GPQA/HLE），我认为未来几年我们会慢慢淡出这类基准，原因有两个。

  1. 它们正变得越来越难以为人类所解读：题目复杂到非专家几乎无法理解在每道题上的表现意味着什么（也难以确认数据集本身不含错误）
  2. 如今模型已经接入互联网访问等工具，潜在知识评测正越来越多地变成网页搜索与检索评测，因此它们本身的意义在下降。简言之，我们正在从闭卷评测走向开卷评测。做个类比：在法国教育体系中，高中是闭卷考试，但进入大学后，通常假定你可以访问数据库和互联网，评分不再那么看重你背下了什么，而更看重你在可以自由获取信息的前提下如何推理。我相信随着模型能力提升，LLM 评测也会出现同样的变化。

数学

数学评测数据集一直被用作推理与逻辑基准测试的代理指标，当然，它们同时也用于检验模型能否解出数学题。

两个参考级的数学评测数据集是 GSM8K（2021），包含小学水平的数学题；以及 MATH（2021），它汇集了网上的奥数题，过去几年里已经达到饱和/数据污染状态。前者后来被几个数据集扩展：GSM1K（2024）用 1K 道新题做了重制，用来检验哪些模型在前者上受到了污染；GSM-Plus 用对抗性改动（干扰项、数值变体等）对题目做了改写；GSM-Symbolic（2024）用得较少，但很有意思，它把 GSM8K 改写成题目模板以防止污染：题目可以无限重新生成。

社区目前主要聚焦于使用以下几类：

  • MATH 的后续数据集，即 MATH-500（采样出的 500 道题的代表性子集，以避免过拟合）和 MATH-Hard（只有最难的 500 道题）
  • AIME（24、25），面向高中生的美国奥数数据集，发布时是什么样就怎么用。这些数据集有意思的地方在于，由于它们由每年更新、难度相当的题目构成，可以通过比较发布时的结果与上一年数据集上的结果来检验数据污染
  • Math-Arena，一份持续更新的竞赛与奥数题汇编，会定期刷新（它包含 AIME25，但也包含很多其他竞赛！）

这些数据集大多其实已经不再”那么难”了，因为它们的难度止步于小学水平（尽管 GSM-Symbolic 允许生成包含更多递归层级的题目，从而在合成层面提高难度）。在另一端，FrontierMath（2024）试图提供难度高得多的数学题，由数学家为此专门逐题编写。该数据集理论上是私有的（但看起来 OpenAI 曾获取到数据集的一部分——真是遗憾）。Humanity’s Last Exam（2025）（已在知识部分介绍过）也包含有意思的”为此次发布专门编写”的数学题，需要复杂推理（尤其是一些定理证明）。

就我个人而言，预训练评测会用 AIME25 和 MATH-500，后训练评测会用 Math-Arena。

代码

由于智能体需要与工具交互，它们必须具备编程能力：如果它们是代码智能体，就要能直接调用工具；或者要能理解在出问题时如何调试工具输出（代码智能体和 JSON 智能体都是如此，二者的区别见这里）。代码评测集也是推理能力不错的代理指标。

回顾历史，2021 年的代码评测集有 MBPP，包含 1K 道众包收集的、仅限 Python 的入门级编程题；APPS，包含 10K 道从编程面试和分享网站中筛选出的代码生成题；以及随 Codex 模型一同推出的 HumanEval，与前面两个不同，它的题目是”专为发布而编写”的，这在当时非常出色！它还附带一个沙箱，以避免在评测者机器上执行有问题的代码。（这篇论文最后还引入了 pass@k 的估计量，在此之前，pass@k 是通过字面检查在 n 次中成功次数是否超过 k 次来计算的。）

EvalPlus（2023）团队制作了 HumanEval+ 和 MBPP+，作为前者的扩展：增加了更多测试用例，修复了原始数据集中的 bug，并补充了更多输入。EvoEval（2024）也对 HumanEval 做了变体，对题目做语义改写并加上难度标注。

对于最终版模型，你可能需要更难或未被污染的题目。

LiveCodeBench（2024）沿用了类似的”从 LeetCode 类网站抓题”的做法，但它非常有意思，因为它记录了题目的日期，从而可以比较模型在训练完成之前和之后创建的题目上的表现。这是一个出色的无污染基准，我很期待它更新！

AiderBench（我想是 2024 年底上线的？）同样使用现有编程网站的数据（具体是 Exercism），但它不止于解题，而是专门测试代码编辑与重构。

对于后训练，你需要更整体的评测，于是有几个基准不再局限于在独立题目上评测，因为那种评测并没有考察复杂的编程能力。RepoBench（2023）测试 Python 或 Java 的仓库级自动补全系统，数据来源是 GitHub 上的代码。它的构建方式是遮蔽代码库中的随机行并要求补全，补全内容要么是跨文件函数，要么是文件内函数，并定义了几个测试层级（检索、补全，以及两者的组合）。

SweBench（2024）是这方面更知名、更完整的版本，同样使用 GitHub，但这次测试的是模型能否解决已有的 issue，因而涉及逻辑理解、跨文件编辑与执行、长上下文推理等能力。

CodeClash（2025）是编程领域的竞技场（arena），模型编写的代码与其他模型的代码相互竞争、编辑并迭代。

此时，我会建议关注 LiveCodeBench、AiderBench 以及 SWE-Bench 中质量更高的子集（SWE-Bench verified），并阅读 METR 报告，了解代码助手在实际使用中的有用性。

长上下文

要在长时间的讨论中与用户正确交互而不迷失线索，你需要良好的长上下文管理。（想想挺有意思：3 年前模型的最大上下文长度还是 2048 token，而如今我们大多已在 128K 及以上。）

2023 年最早开始测试这一点的评测大概要数 NIAH（Needle in a Haystack，大海捞针）：把一条随机事实放进一段很长的无关文本中，要求模型把它检索出来。它提供了一个简洁的框架，用来评测模型最容易在上下文的哪个位置遗忘信息，以及从多长的上下文开始遗忘。2023 年模型在这上面表现很差，到 2025 年已接近解决。

此后出现了更复杂的长上下文扩展。RULER（2024）加入了多跳追踪（要求模型沿变量链追踪以取得正确取值）、词频变化，并增加了 NIAH 的问答变体。它如今也接近解决。Michelangelo（2024，有时也被称为 MRCR，即 multi round co reference）同样使用合成长上下文数据：任务（长度各异）测试模型能否精确复现上下文中独一无二的片段（以及判断相关信息是否存在），并理解一段文本的修改序列。它随后在 OpenAI MRCR（2025）中得到扩展。InfinityBench（2024）是多语言的（英文和中文），提供 100K token 的合成数据任务，覆盖多种目标（问答、类似 NIAH 的检索、超长上下文上的计算……）。InfinityBench 仍然能提供一些信号。

HELMET（2024）把任务与既有基准组合起来，得到一个信号更丰富的大型单一数据集：RAG 与问答数据集（Natural questions、TriviaQA、PopQA、HotpotQA、Narrative QA 和 InfinityBench）、召回（RULER 和 JSONKV）、带引用的生成（ALCE 的子集）、摘要、段落重排（MS MARCO）、上下文学习（TREC、NLU、Banking77、CLINIC150）。基准聚合很全面，但存在重复度量的风险：比如，不要既用 HELMET 又用 InfinityBench 测你的模型，再把结果聚合起来，因为那等于把同一项评测跑了两遍！在 2025 年，它仍有足够的区分度来比较模型。

我最喜欢的长上下文评测思路是 Novel Challenge（2024）——针对过去一年出版的虚构类书籍的 1K 条真/假陈述（由这些书的读者撰写！），必须读过并理解全文才能正确作答；以及 Kalamang 翻译数据集（2024）——模型需要先读一本语法书，再从英文正确翻译成 Kalamang（Kalamang 是资源极稀缺的语言，网上完全没有它的资料——只有 200 名使用者）。Kalamang 翻译集显然可以扩展到其他低资源语言（不过更酷的是扩展为使用基于规则的语法检查器来检验生成的有效性，从而得到严格的准确率，而不是依赖 BLEU……）。

指令遵循

两个主要的指令遵循数据集是 IFEval（2023）及其扩展 IFBench（2025）。在我看来，IFEval 是近几年最聪明的评测思路之一：模型被要求遵循格式指令（涉及关键词、标点、词数/句数、markdown 或 html 等文件类型格式，等等）。每一条这样的条件都能用一个特定的解析测试来检查：这意味着该评测是少有的自由形式生成式评测之一，能拿到严格分数而不依赖模型裁判。

更一般地说，它属于功能正确性/单元测试这一评测类型，这也是我个人最喜欢的模型评测方式。它也很容易重新生成或扩展，以防止数据污染。

顺带一提，有些基准也测试“非指令遵循”（不遵从）：CoCoNot（2024）尤其会测试模型面对不完整（欠指定/不清晰）、无法回答（因信息缺失，或是在把 AI 拟人化，常常会诱发幻觉）、或不安全的请求时，是否会拒绝遵从。它先由人工撰写查询、再由模型撰写不遵从的请求，然后经过过滤，构建出一个以分类问题形式呈现的评测集。

工具调用

工具的出现，是推动 LLM 迈入智能体领域的功能之一。

TauBench（2024）评测模型在零售和航空领域回答用户查询的能力（下单/预订/查商品等）。数据库用合成样本模拟真实领域数据，只有当 1）模型的动作正确更新了数据库、且 2）它恰当地回答了用户时，才算正确。为了让该基准自动化，用户由 LLM 扮演，这使得该评测运行成本相当高，且容易出错。尽管有这些局限，它仍被广泛使用，尤其是因为它能很好地反映真实用例。

ToolBench（2023）要求调用 API（OpenWeather、Cat、HomeSearch、TripBooking、GoogleSheets、WebShop、Tabletop 等）来求解数据集中的 100 个测试用例，每个用例需要 1 到 10 次工具调用。这些 API 有些是模拟的、有些是真实的，这使得该数据集容易因意外故障而出错。因此它在 StableToolBench（2025）中被修复并扩展：后者引入通用的 VirtualAPIServer，把所有东西都模拟出来，以保证评测稳定性，但评测依赖 LLM 裁判，又引入了另一层偏见。

BFCL（2025，但该基准实际上已有几年历史）在这一年里演进显著，当前版本包含 4 个子集：单轮（简单工具调用）、来自用户的众包真实函数调用、多轮对话（测试长上下文中的准确率以及借助工具调用回答查询），以及智能体式（网页搜索、记忆、SQL 数据交互）。它结合抽象语法树、执行响应和状态匹配（最终状态是否为期望状态）来判断调用是否正确。人们关注 v3 来专门测试工具调用，而 v4 测试网页与搜索工具的使用。

最后，随着 MCP 的出现，也涌现了一些测试面向 MCP 的工具调用的基准——但它们大多依赖模型裁判，并使用真实世界的 API，这可能因网络问题带来潜在的失败情形/可复现性缺失（看起来给网站创建者增加的负载不算大问题，因为多数被 MCP 覆盖的服务用户群足够大）。

MCPBench（2025）把 LLM 连接到实时、真实世界的 MCP 服务器（Wikipedia、HF、Reddit、Steam、arxiv……），任务需要多轮才能解决（任务为合成生成）。该评测把对工具调用有效性与成功与否的、基于规则的检查，与用来评估查询是否得到恰当回答的 LLM 裁判结合起来。

MCP-Universe（2025）使用了 11 个 MCP 服务器，覆盖各种现实世界主题（现实场景导航、3D 设计、网页搜索等）。这个基准有意思的地方在于，评测依赖多个严格的评估器：一个检查格式正确性，两个检查答案正确性。由于任务可以是静态的（询问不会变化的信息）或动态的（某个仓库的 GitHub star 数、天气……），在后者的情况下，答案正确性由一个依赖具体任务的、基于执行的评测框架来判断，该框架会自动从相关来源获取最新的正确答案，并将模型输出与之比较。这比依赖 LLM 裁判要清爽得多！

LiveMCPBench（2025）提供了一个规模庞大、可本地部署的 MCP 服务器集合，用于测试模型在区分不同工具以完成任务方面有多强。最好的模型已经达到 80%——所以我们已经接近饱和了。不过，测试模型能否在非常长的工具列表中选出合适的工具，是一个很好的用例，随着网络逐渐 mcp 化，这一点会越来越重要。

（顺便说一句，这里有一篇关于如何编写好工具的精彩文档。）

测试单项能力能提供有价值的信号，但真实场景中的助手表现来自这些能力的组合方式。一个模型可能擅长推理，但当推理必须同时与工具调用和长上下文管理结合时就会失败，因此我们需要那些要求同时编排多种能力的评测。

助手任务

我认为 助手任务将成为开展更进阶评测的主要方式之一：解决这类任务需要多种能力的组合（长上下文、推理、工具调用……），而基准本身能在有用的真实场景设置中，提供关于特定领域表现的洞见。相比具体能力基准，它们通常也更容易（被普通大众）理解。如果基准足够通用，它们不会检查使用了哪些具体工具，而是检查最终结果是否正确，因为复杂任务允许多条通往成功的路径。

真实场景信息检索

GAIA（2023）通过要求模型组合使用工具、推理与检索来解答真实查询（有时还包含文档），开启了现代智能体评测。问题被分为 3 个级别，第一级如今已饱和，第三级对模型来说仍然困难。它也是那种你找到的数字会因评测方法而分散的基准之一，因为人们要么报告公开验证集上的结果，要么用 LLM 裁判在私有测试集上评测（公开排行榜在这里）。

后来 BrowseComp（2025）复现了这一思路，测试的是同一件事（模型能否借助工具和在线信息，为特定查询找到恰当的答案），但不保证结果的唯一性，因为问题是从结果出发反向构造的，难度各不相同：例如，要检索某篇特定论文，问题会通过组合元数据信息来构造，比如“哪篇关于 Topic 的论文发表在 Conference 上，作者中有一位 Nationality 国籍的人，另有两位来自 Entity？”不过，这个基准目前大概也更难。

GDPval（2025）在来自“对美国 GDP 贡献最大的行业”的 44 种职业上评测模型，使用模型裁判将模型表现与人类表现进行比较。

最后，GAIA2 超越了简单的信息检索，使用一个模拟的移动端环境，测试助手能否正确回答依赖事件链与工具调用的查询。就目前而言，对模型来说最难的是时间敏感以及刻意加入噪声（模拟 API 调用失败）的子集，而搜索与执行对 SOTA 模型来说似乎极其简单。

科学助手

SciCode（2024）测试模型能否通过编写恰当的科学代码来解决现实中的科学问题，覆盖多个 STEM 领域（从生物学到数学、化学……）。题目取自真实工作流程，每个核心问题都被分解为更简单的子问题。第一版的评测由科学家和模型裁判完成——在论文发表时模型表现相当差（得分不足 5%），但我不确定在哪里能找到最新的结果。

PaperBench（2025）同样测试模型能否复现机器学习研究，但这次的设置更难：给定 ICML 的高质量论文，模型必须重建与之对应的代码库（论文作者贡献了 8000 个单独评分的任务，按评分标准树组织，并对最终评分加权）。该基准用 LLM 裁判评测（不过我怀疑，只要稍微约束所要求代码的形态，其中一部分可以自动完成）。

DSBench（2025）是一个多模态数据分析基准，使用 Kaggle 与 ModelOff（金融数据）的样本。从附录中的示例看，ModelOff 的题目似乎以多项选择的形式给出，这很可能让任务更简单，而 Kaggle 的任务各自有自己的指标。

DABStep（2025）在以往属于私有（因而未被污染）的运营数据分析工作负载上评测模型，使用真实的提问与数据。所有题目都需要多步推理和多样化的文档解析，当然还需要特定的数据操作技能。这是一个很棒的评测，因为它很难，且复现了真正有用的真实用例；而且每道题都有标准答案，所以评测无偏且成本不高。

助手任务在贴近现实的场景中测试综合能力，但它们要么是动态且只读的，要么处于不会变化的环境之中。要评测适应性与动态决策，我们需要能够“给模型带来意外”的环境。

基于游戏的评测

基于游戏的基准非常有意思，原因有几个：它们通常评测对变化环境的适应能力（与大多数静态的助手任务相反），需要长上下文推理，而且最后同样重要的是，它们易于理解。然而，它们并不扎根于现实生活，也未必能反映在真正有用的用例上的良好表现。

其中最有名的正式评测大概是 ARC-AGI。第一版（2019）由一系列谜题网格组成，模型必须在没有明确给出规则的情况下找出该序列的最后一项。在我看来，这个基准很像面向逻辑的智商测试，它在 2024 年几乎被解决。一个类似的基准（规则外推）是 Baba is AI（2024）。该基准的最新版本 ARC-AGI3（2025，进行中）仍在开发中，包含专门为该基准打造的全新游戏（需要探索、复杂规划、记忆管理……）。它仍在进行中，目前在已公布问题上的最佳解法是对游戏进行暴力穷举。

社区与模型提供方已经探索了一批用 LLM 玩现有游戏的做法。单人冒险类游戏/RPG，比如 TextQuests（2025）或 Pokemon（2024）（例如 Claude 与 Gemini 的 Twitch 直播），要求模型把超长程规划与达成目标结合起来，而这需要恰当的长上下文记忆管理、推理和回溯能力。单人生存类游戏，比如 Crafter（2021，灵感来自 Minecraft），也需要同样的能力。已有相当数量的单人游戏环境被整合进 Balrog（2024）基准。

竞争性诈唬类游戏，比如 Poker（2025）、Town of Salem（2025）这类黑手党变体、Werewolf（2025，见此处/彼处），或者 Among us，对于测试逻辑、推理以及欺骗能力都非常有意思。例如，Claude Opus 4 在扮演吸血鬼（欺骗性角色）时无法赢下 Town of Salem，但扮演农民（非欺骗性角色）时表现不错。合作类游戏，比如 Hanabi，也可以用来测试受限环境下的适应性与沟通能力。

这些游戏还有一个很妙的地方：它们有单一且毫不含糊的通过/失败指标——LLM 到底有没有赢下这局游戏？目前，如果我要用它们来评测模型，我大概会看 TextQuests 来测能力，看 Town of Salem 来测安全。

除了在受控环境中测试能力，人们还探索了终极的无法作弊的任务：预测未来。

预测者

过去一年里，出现了一类全新的、无法被污染的任务：预测。（我猜严格来说，股票市场预测可以通过某些操纵来作弊，但希望我们还没走到有财务动机去搞坏评测的那一步。）它们应当要求模型跨多个来源推理，以尝试解答尚未发生的事件相关问题，但这些基准是否有足够的区分度、能带来足够强的价值，目前并不确定；而且它们很可能强化 LLM 那种“老虎机式成功”的感觉。（模型在某些事件上的表现接近随机，是因为这些事件本就无法预测，还是因为模型不擅长？反过来，如果模型能正确预测某个事件，是这个问题太简单，还是太套路化？）

FutureBench 测试模型能否预测未来会登上新闻的事件。它使用两类来源：浏览网页，以及由 LLM 生成、时间跨度为每周的问题；再加上来自博彩市场的用户预测。所有数据在使用前都会经过大量过滤与清洗。目前，在人类创建的赌注上，模型仅比随机略好；在模型生成的问题上，成功率约为 3/4（这些问题很可能更容易）。

FutureX 与之类似，但使用的是一组特定网站（预测市场、政府网站、通用排名网站和实时数据平台），然后用模板生成关于潜在未来事件的问题（when will STOCK reach POINT?）。每天生成 500 个问题，并会过滤掉意外不相关的问题。

Arbitrage 中生成问题也采用了类似思路，核心差别在于时间跨度：那里的问题应当到 2028 年才会揭晓结果。

顺着相似的路子，你还会看到一些竞技场：给 LLM 提供资金，让它们主动在金融市场上交易（比如 Alpha Arena 或 Trading Agents）——这类实验不太可能给出有意义的结果，因为受成本所限，它们往往每个模型只跑一次，于是你无法获得任何统计显著性。

TLDR

随着能力的一次次跃升，评测的格局也在演变：从测试孤立技能，转向在更贴近现实的场景中衡量综合表现。

截至 2025 年 11 月，我推荐使用：

  • 核心能力（面向模型构建者）：训练阶段仍然用旧的能力评测；后训练阶段用 AIME26（等它发布后）、GPQA、IFEval、SWE-Bench，以及一个你自己选择的长程评测，比如 HELMET、TauBench，或者如果你面向工具使用，就用 BFCL
  • 核心能力（用于推理阶段比较模型）：IFBench、HLE、MathArena、AiderBench 和 LiveCodeBench、MCP-Universe
  • 长程任务（衡量真实世界表现）：GAIA2、DABStep、SciCode，或针对你的用例做领域特定评测
  • 游戏（为衡量鲁棒性与适应性增添一点乐趣）：ARC-AGI3（等它发布后）、TextQuests、如果你关心安全就用 Town of Salem，或者任何你喜欢的、能超越 Poker/Chess/Go 的游戏。

这个领域正朝着测试能力编排、而非孤立技能的评测方向走，目的是贴近实际使用。这与我们构建“好用”模型的目标一致——所谓好用，就是能可靠地把核心能力、工具使用与良好的编排结合起来解决实际问题的系统。

我希望这个领域能更重视函数式测试，而不是模型裁判；同时更重视普通人也能看懂的数据集与任务。

弄清里面都有什么

无论你如何挑选初始数据集，最重要的一步始终是查看数据——既包括你手头的数据，也包括模型生成的内容及其得分。归根结底，只有这样才能看出你的评测是否真的与你的具体用例相关。

你需要研究以下几点。

数据创建过程

  • 实际的样本是谁创建的？ 理想情况下，你希望数据集由专家创建，其次是付费标注者，然后是众包，再然后是合成数据，最后是 MTurk 众包。你还要找一找数据卡，在那里你能看到标注者的人口统计信息——这对于理解数据集的语言多样性或潜在的文化偏见可能很重要。

  • 它们是否都由其他标注者或作者检查过？ 你想知道样本上的标注者间一致性分数是否很高（= 标注者之间是否一致？），以及完整数据集是否被作者检查过。 对于借助低报酬标注者（这些人通常不是目标语言的母语者，想想 AWS Mechanical Turk）构建的数据集，这一点尤其重要，否则你可能会发现拼写错误、语法错误或毫无意义的答案。

  • 是否为标注者提供了清晰的数据创建指南？ 换句话说，你的数据集是否一致？

样本检查

随机抽取 50 个样本并手动检查；我的意思是你亲自去做，而不是“提示一个 LLM 帮你找出数据中不寻常的内容”。

首先，你要检查内容质量。

  • 提示词是否清晰无歧义？
  • 答案是否正确？（例如：TriviaQA 每道题包含多个标准答案（aliases 字段），有时彼此冲突。）
  • 是否缺少信息？（例如：MMLU 中有若干题目引用了并不存在的图表。）

要记住，一个数据集是标准，并不意味着它就是好的——而这种情况之所以发生，是因为大多数人都跳过了这一步。

然后，你要检查它与你的任务的相关性。这些问题是你想要用来评测 LLM 的那类问题吗？这些例子与你的用例相关吗？

你可能还想检查样本的一致性（尤其是如果你打算使用少样本提示或计算聚合统计量）：如果是多项选择评测，所有样本的选项数量是否相同？提示词前后的空格是否一致？如果你的评测附带额外的环境，理想情况下你应该用它来理解实际调用的是什么。

最后，你还要快速检查里面有多少个样本（以确保结果具有统计显著性——对于自动基准，100 个样本通常是下限）。

例如，在下面的查看器中，你可以检查 Lewis 收集的知名后训练基准的前几个样本。

任务与指标

你要检查使用了哪些指标：是自动指标、函数式指标，还是使用模型裁判？答案会改变你运行评测的成本，也会影响可复现性和偏见类型。最好（但也最罕见）的指标是函数式指标，或基于规则验证器的指标

做代码评测时，当心过于简单的通过/失败单元测试！近期的 LLM 已经非常擅长覆盖全局变量来“作弊”，尤其是在 Python 这类可以扰乱变量作用域的语言中。

所以，你无法复现公布的模型分数？

假设你读了一份关于某个很酷的新模型的近期技术报告，想在自己的机器上复现他们的结果……却怎么也复现不出来？ 我们来探究一下原因。

不同的代码库

要把评测分数复现到小数点后几位，你首先需要确保自己使用的代码库与你想复现的论文所用的代码库完全一致。

通常，这意味着要么使用作者提供的评测默认代码，要么使用参考库中的标准实现，比如 Eleuther 的 AI lm_eval 或 HuggingFace 的 lighteval。然而，如果没有提供评测的代码来源，那我只能为你感到遗憾——你不太可能精确复现这些结果。

如果你想轻松了解使用不同实现时会出现什么样的差异，可以看看我们与 HuggingFace 评测团队合写的这篇博客（⭐）。它研究了我们观察到的 MMLU 评测的 3 种常见实现（lm_eval、helm 以及原作者实现）之间的差异，以及它们如何改变模型分数。

细微的实现或加载差异

我们观察到，以下这些事情很容易出错，即便使用的是同一个代码库：

  • 不同的随机种子。
    • 通常，推理受随机种子的影响比训练小。不过，它们仍会影响某些 CUDA 操作（参见 PyTorch 关于可复现性的页面），并且如果你使用非贪心的生成策略，还会改变预测结果。如果你使用少样本示例，它们也可能影响提示词，以及一些前处理或后处理函数。 -> 微小的改动就可能带来几个点的差异。
  • 实际上是不同的指标。 即使名称相同，指标在实践中也可能不同。一些例子：
    • 如果原始实现是基于对数似然的 exact match（计算不同可能答案的对数概率），而你使用的是生成式的 exact match（只把主要的贪心生成结果与参考进行比较），你得到的分数就不会相同。
    • 我们还在一些评测代码库中看到，许多任务被定义为 exact match，实际上是 prefix exact match（只比较生成结果的开头与参考）、suffix exact match（恰好相反）或 quasi exact match（带归一化的精确匹配）。 -> 因此，你不能只依赖指标名称来判断发生了什么，而需要查看代码。
  • 不同的归一化。
    • 回到我们上面 exact match 比较的例子，在 lm_eval v1 中，许多任务被简单命名为生成式 exact match：你会由此以为预测是照原样与参考进行比较的。 但查看代码会发现，预测在与参考比较之前要先经过一步归一化（去除标点、统一数字格式等）。这显然会大幅改变结果。 （lm_eval v2 现在在大多数指标名称中包含了归一化名称。） -> 这是最容易搞错的事情之一，尤其是对那些需要大量归一化/答案后处理的任务，比如数学评测（你需要从生成的解释中抽取答案）。
🔧
模型加载影响可复现性

即使代码相同，也有四个因素会改变结果：

  • 硬件：PyTorch 不保证在不同 GPU/硬件上可复现
  • 推理库：截至 2025 年，transformers、vllm 和 sglang 对批处理和矩阵运算的处理略有不同
  • 批大小：不同批大小 = 不同结果（为了保证可复现性，你应当固定批大小，但要小心 OOM 错误）
  • 加载精度：更低的精度（尤其是量化模型与浮点模型相比）会改变数值结果

不同的提示词

提示词的变化可能涉及 3 个主要方面。

提示词本身

你用于提示词的格式可能而且确实会大幅改变分数。

例如，对于多项选择问题，常见格式包括非常简单的变体（例如用 A、A.、A) 来引出选项），这些变体虽然语义等价（内容完全相同），却仍可能导致同一模型出现好几个点的差异。

提示词格式敏感性

我们对此做了一些实验（在语义等价的提示词上，同一模型最多可看到 7 个点的差异，即最右侧的 5 列），并且一篇论文观察到了类似的结果。

另一个例子：Llama 3.1 模型能给出正确的 MATH-Hard 答案，但在 Open LLM Leaderboard 上得分很低，因为它们过拟合了 GSM8K 的提示词格式，无法适应这次评测的新格式，尽管该格式已通过少样本示例提供。

这篇出色的论文⭐ 也指出了这一点的一个副作用：现在有许多模型被训练成过拟合基准的提示词和答案格式，代价是在评测时对其他提示词的适应能力。

有些任务还会在前面加上任务提示词（例如 The following questions are about <topic>）——它存在与否同样会影响分数。

系统提示词与对话模板

对话模型通常经历过指令/偏好训练或微调。在这一阶段，它们学会了在推理时遵循特定的模板。例如，模板可能要求对话轮次以一段通用提示词（称为 system prompt）开头，并带有特定 token 作为前缀（通常是 System: ）。该提示词用于为模型提供高层指令，例如人设的内容，或通用的回答风格指令。对话轮次还可能要求在文本中加入前缀关键词，例如用 User 表示提问、用 Assistant 表示回答。

使用少样本时，你还需要选择示例是以多轮形式提供（模拟用户/助手轮次），还是一次性提供（放在单个用户提示词中）。

在推理时不遵循模型期望的对话模板会严重损害其表现，因为这会把它输出推到其收敛所在的概率空间之外。

同样，如果你使用的是推理模型，需要确认你比较的是开启还是未开启思考模式的结果。

少样本示例

少样本示例有两件事容易搞错：少样本示例的数量、你使用的是哪些示例，以及它们的具体顺序。

使用相同的示例之所以重要，并不太令人意外——前提是我们假设某些样本比其他样本更能表达任务。也许更令人意外的是：你不仅需要使用完全相同的样本，还必须以完全相同的顺序呈现它们。在相同样本上改变顺序，让我们在 MMLU 的某些子集上观察到最多 3 个点的差异（你可以在这里看到一些结果，是第三个颜色网格图）

这也是需要关注随机种子的地方。

参数

对于生成式评测，需要关注的参数是确保你：1）使用相同的句子结束 token（对于对话模型和推理模型，你大概不应使用默认的那个）；2）允许模型在评测中生成相同数量的 token（这对推理模型尤其关键，它们在思考模式下需要大量 token）；3）如果使用采样，确保使用相同的随机种子/温度参数。

为模型训练自动挑选好的基准

在某些情况下，你并不想“仅仅”事后复现已有的分数，而是需要了解模型在训练过程中表现如何。此时你需要的评测具有与评估模型最终表现的评测不同的性质，因为你需要那些即使在模型还不够好时也能提供良好信号的任务。

因此，FineWeb 团队设计了一种方法，用于在 9 种语言中选出最适合预训练消融实验的评测——让我们听听他们明智的建议。

对于这些语言，我们收集并实现了能找到的所有可用任务，共 185 个任务。然后，我们以两个主要目标开始任务选择：确保评测多样性，以及确保每个任务在预训练期间提供可靠的信号。

对于评测多样性，我们旨在评估广泛的模型能力，包括：

  • 阅读理解（RC）：理解所提供的上下文并据此回答问题。
  • 常识（GK）：在没有额外上下文的情况下回答各领域的事实性问题。
  • 自然语言理解（NLU）：理解所提供输入的语义。
  • 常识推理（RES）：展示执行需要具身知识的简单推理的能力。
  • 生成式任务：在没有多项选择选项“帮助”的情况下用目标语言生成文本的能力。

我们认为，如果任务能给出可靠的分数，就说明它提供了可靠的信号。这意味着分数应高于随机基线、随训练推进而上升、在不同随机种子间波动较小，并在每个训练步上给出稳定的模型排名针对规模相近、使用相同超参数并在相同数据量上训练的模型。。

为全面考察这些任务提供的信号，我们针对每种语言训练了多个 1.5B 参数模型，每个模型使用 30B token，取自五个最大的公开多语言网络数据集所支持语言的子集。这些模型使用相同的超参数和分词器训练。随后，我们在固定的 checkpoint 间隔上，用收集到的任务对它们进行评测（在零样本设置下，不使用指令，也不使用系统提示词）。

由于任务实现经过多轮迭代，这一过程对每个任务都需要多次评测运行，最终总共消耗了 73 000 GPU 小时 🔥！

在训练了 49 个模型之后，我们终于可以定义对我们而言可靠信号意味着什么！

单调性

我们对任务的核心要求之一是：它能够从训练数据中被学到，并且这种学习能随着训练推进被逐步观察到。如果随着时间推移没有这种提升，就无法确定未来是否会出现提升。

为衡量这一点，我们使用 Spearman 秩相关来量化训练步数与分数之间的相关性。即使分数不随步数线性变化，Spearman 秩相关也能刻画单调性。我们要求每个任务在所有模型训练运行上的平均相关系数至少为 0.5。

低噪声

比较模型在任务上的表现时，我们需要考虑差异究竟来自评测噪声，还是真实的性能差异。

噪声可能来自模型训练中的随机过程，例如随机 token 采样、数据打乱或模型初始化（Madaan et al., 2024）。为衡量每个任务对这种噪声的敏感程度，我们使用不同的随机种子，在我们自己的单语语料（各语言未经过滤的 CommonCrawl 数据）上额外训练了四个模型。

对每个任务，我们计算了：

  1. 首先，计算每个训练步（大约每 1B token）上模型分数的标准差，我们称之为 per-step-std。
  2. 然后，为得到全局的波动性度量，我们对所有 per-step-std 值取平均，得到整个训练过程中的 avg-std。我们假设该值是跨模型架构和训练数据集的上界（因为它由在“更脏”的数据集上训练的模型近似得出，因而波动性更高）。
  3. 最后，我们计算信噪比（SNR），作为任务波动性的主要指标。SNR 的计算方式为：所有运行在 30B token 时的平均分数除以 avg-std。该指标衡量整体分数相对于分数波动（噪声）的显著程度。

我们希望每个任务的 SNR > 20。这条规则的唯一例外是生成式任务，它们的 SNR 通常相对较低，但仍值得纳入，因为它们能揭示模型在被要求进行无约束生成（没有答案选项）时的行为。在多语言场景下这一点尤其重要，因为某些在多种语言上训练的模型可能在任务上取得高分，却在生成式任务中突然用错误的语言回答！

假设模型性能在不同随机种子间服从正态分布，我们希望基准运行的表现至少比基准随机基线高 3 个 final-std。这意味着 99.85% 的种子分数高于随机基线（形式上，基准运行的表现 - 基准随机基线 > 3 * final-std）。

非随机性能

许多模型能力是在训练后期才获得的，因此许多任务（尤其是更难的、比如与数学相关的任务）会在很长一段时间内只表现出基线水平。这些任务虽然有用，但并不适合早期的预训练评测，我们不希望在该场景中保留它们。

我们首先计算任务的随机基线表现（对多项选择题，为所有样本的 1/n_choices 之和；对生成式评测，为零）。然后计算任务相对基线的距离，即所有模型中的最高分减去基线。

模型排序一致性

别忘了，这些评测的主要目标是比较模型和数据集！

未来，我们希望用这些评测为完整的模型预训练挑选最佳数据集。这意味着我们的任务对用极少 token 训练的数据集所做的排序（我们通常在 30B token 上运行数据消融实验），应当与它们训练更长时间、经过显著更多步之后的排序一致。

换句话说，我们希望任务具备对预训练期间未来表现的预测能力：如果预训练数据集 A 在 30B token 时优于预训练数据集 B，我们希望这一趋势能延续到 300B token。

要证明这一点本质上是不可能的，但存在一个我们可以检验的必要前提条件：结果若要在更大规模上保持一致，首先必须在较小规模上也表现出一致性！

为衡量任务排序的这种一致性，我们计算了每两个相邻训练步之间模型排名的平均 Kendall’s Tau。我们只考虑预训练 15B token 之后的训练步，因为发现该范围之前的排序噪声极大。该指标取值高，说明排序随训练推进保持一致。

我们对这一属性没有严格的最低值要求，而是用它来在任务之间建立比较。

由于多项选择任务中 CF 的目标就是选项本身，每个目标的 token 数、字符数以及无条件概率（在没有上下文前缀的情况下生成该选项的概率）都可能不同。

acc_pmi 指标衡量的是：与完全没有上下文相比，模型在获得问题上下文时预测 A_i 的可能性高出多少。当正确选项包含通常不太可能出现的 token，从而使模型不太愿意选择该答案时，这一指标会很有用。

另一方面，对于生成式任务，我们使用了以下指标：

  • prefix_match：只需答案前缀匹配的精确匹配
  • f1：基于使用词级分词器抽取的预测词与标准答案词计算的 F1 分数

对这两个生成式指标，都会做少量预处理：去除冠词和标点，并将文本转为小写。

选择最佳评测指标被证明是一项颇具挑战的任务。不仅没有任何一个指标能始终优于其他指标，我们还常常遇到这样的情形：某个指标的单调性更好，而另一个指标的信噪比更高。在这类情况下，我们通常参照该任务在其他语言实现中所选用的指标来做出决定。我们清楚这种手工挑选往往并不可行，因此给出以下建议：

➡️ 多项选择任务

  • 我们发现，对于答案选项差异细微的任务（例如 Yes/No/Also），基础准确率表现良好，NLI 任务尤其如此。在这类答案选项通常各为一个 token 的情况下，建议使用基础准确率。
  • OLMES 的作者（Gu et al., 2024）建议对含有不常见词的任务使用 PMI，但我们发现 PMI 对 AGIEVAL 或 MMLU 这类“困难”的推理与知识任务非常有效。在这些情形中，PMI 给出了最佳结果，而且往往是唯一能让表现超过随机的指标。话虽如此，PMI 在其余所有任务上的平均表现是最弱的，同时计算成本还是其他指标的两倍。因此我们只建议在复杂推理与知识任务中使用它。
  • 我们发现整体最可靠的指标是基于长度的归一化指标（按 token 或按字符）。但最佳选择取决于语言，而不是对某个给定任务保持一致。因此，为了获得最可靠的结果，我们建议取 acc_char 与 acc_token 中的最大值。注意 acc_token 高度依赖分词器。在我们的消融实验中，所有模型都是用同一个分词器训练的。

➡️ 生成式任务

对于生成式指标，选择就清晰得多：除非像数学类任务那样需要精确匹配，否则我们建议使用 F1 分数。F1 通常噪声更小，对生成结果的微小变化也更稳健。

创建你自己的评测

到了这一步，你大概已经清楚人们为什么要做评测、有哪些基准、以及哪些基准与模型的不同阶段相关（训练、基座模型和微调模型的推理），但如果你特定的用例没有任何现成的东西呢？

这正是你可能想要创建自己的评测的时候。

数据集

使用现有数据

你可以按原样使用现有数据集，并更改相关的提示或指标（正如为适配新的提示方法而对较早的评测所做的那样），但你也可以聚合数据集。

当你想评测某项特定能力、而单一基准未能很好地覆盖它时，数据集聚合是个好办法。与其从零开始，你可以把多个现有数据集的样本组合起来，构建一套有针对性的评测集。例如，“Measuring AGI”论文的作者最近就这么做，试图创建一个新的“AGI 评测”数据集。

聚合数据集时，要注意以下问题：

  • 它们是否包含冗余数据（大多数数学数据集都是对同一批初始问题的改写或聚合）
  • 你需要在各来源之间保持均衡的代表性（你可能不希望某个数据集占据主导并扭曲你的评测）——这也决定了分数是按全部样本聚合，还是按各个子集聚合
  • 格式与难度级别是否兼容（通常来说，构建统一数据集时，要小心混合那些需要采样和不需要采样的样本）。
示例：MMLU、Big-Bench（数百个多样化任务）以及 HELM（组合多个现有基准做整体评测）

EpochAI（2025）的新研究展示了如何在单一框架下最好地聚合基准，使聚合后的数据集整体上更难，也更不容易饱和。

使用人类标注者

我建议读一读这篇关于数据标注质量良好实践的综述的第 3 节。如果你想要生产级质量，并且有条件实施所有这些方法，那就放手去做！

不过，无论你的项目规模大小，一旦你定义好任务和评分指南，以下这些重要准则都适用。

  • 人员筛选，以及（如果条件允许）金钱激励 你很可能希望参与你任务的人：
  1. 符合某些人口统计特征。 一些例子：是目标语言的母语者、受过更高水平的教育、是某个特定领域的专家、地理来源多样，等等。 你的需求会因任务而异。
  2. 产出高质量的工作。 如今尤其重要的是，要加入一种检查答案是否由 LLM 生成的方法，并且你需要把某些标注者从你的池子里筛掉。 在我看来，除非你指望的是积极性极高的众包标注者，否则给标注者支付合适的报酬总是更好的做法。

除非你拥有积极性极高的众包标注者，否则一定要支付公平的报酬。报酬过低的标注者产出的工作质量更低、引入更多错误，还可能用 LLM 快速完成任务。

  • 指南设计 一定要投入大量时间去真正地头脑风暴你的指南！在 GAIA 数据集上，这是我们投入时间最多的环节之一。

在创建 GAIA 基准时，指南设计比其他任何阶段都更耗时。清晰、无歧义的指南值得这份投入——它们能避免代价高昂的重新标注轮次。

  • 迭代式标注 要做好进行多轮标注的准备，因为你的标注者会误解你的指南（它们比你想象的更含糊）！多次生成样本能让标注者真正收敛到你需要的标准上。

    • 质量估计与人工筛选 你需要对答案进行把控（尤其是通过标注者间一致性——如果你能拿到的话），并做最终筛选，只保留质量最高/最相关的答案。

Argilla 这类用于构建带标注的高质量数据集的专用工具也能帮到你。

实用技巧与提示

以下是使用人工标注者构建评测数据集时，你可能需要考虑的一些实用技巧。

设计任务

  • 越简单越好：标注任务很容易变得不必要地复杂，所以要尽可能保持简单。把标注者的认知负荷降到最低，有助于确保他们保持专注，并做出质量更高的标注。
  • 检查你展示的内容：只展示标注者完成任务所必需的信息，并确保不包含任何可能引入额外偏见的内容。
  • 考虑标注者的时间：内容的展示位置与展示方式可能带来额外的工作量或认知负荷，进而对结果质量产生负面影响。例如，确保文本与任务同时可见，避免不必要的滚动。如果你把多个任务组合起来，且一个任务的结果会影响另一个任务，可以将它们按顺序展示。思考标注工具中所有内容的呈现方式，看看是否还有进一步简化的空间。
  • 测试整套设置：任务设计完成、指南就位之后，务必先在少量样本上自己测试一遍，再让整个团队参与进来，并按需迭代。

标注过程中

  • 标注者应独立工作：最好让标注者在任务期间互不帮助、也看不到彼此的工作，因为他们可能传播自己的偏见，导致标注漂移。对齐应始终通过完整的指南来实现。你可能需要先在一个单独的数据集上培训新成员，和/或使用标注者间一致性指标来确保团队已经对齐。
  • 一致性是关键：如果你对指南做了重要修改（例如修改了某个定义或指令，或者增加/删除了标签），要考虑是否需要重新处理已标注的数据。至少，你应当通过类似 guidelines-v1 这样的元数据值来跟踪数据集中的变更。

人机混合标注

有时团队面临时间和资源上的限制，但又不想牺牲人工评测的优点。在这种情况下，你可以借助模型让任务更高效。

  • 模型辅助标注：你可以把模型的预测或生成结果用作预标注，这样标注团队就不必从零开始。只需注意，这可能会把模型的偏见引入人工标注；而且如果模型的准确率很差，反而可能增加标注者的工作量。
  • 以模型为裁判并加以监督：你可以把“模型作为裁判”方法的能力（见“模型作为裁判”一节）与人类监督者结合起来，由后者验证或丢弃结果。注意，“人工评测的优缺点”中讨论的偏见在这里同样适用。
  • 识别边界情况：想要更快的任务流程，可以使用一组模型组成的评审团，然后让人类监督者在模型出现分歧或打平时介入裁决。同样，要留意“人工评测的优缺点”中讨论的偏见。

合成创建数据集

使用基于规则的技术

如果你的任务允许，使用程序化生成的基准是获得近乎无限样本并避开数据污染的好办法！它们能以算法方式生成无限多全新的测试用例，同时控制难度并支持自动验证，确保模型在训练中没见过这些样例。

一些例子可以看 NPHardEval、DyVal、MuSR、BabiQA、ZebraLogic、IFEval 或 GSMTemplate 等。NPHardEval 生成以复杂度为基础的任务，比如带自动验证的图问题，并每月刷新以降低过拟合。MuSR 使用神经符号生成来创建复杂的推理实例，比如 1000 词的谋杀谜案。ZebraLogic 通过生成解并用 SAT 求解器迭代最小化线索，以算法方式产出逻辑网格谜题。BabiQA 模拟实体执行一连串动作。IFEval 用 500 多个包含可程序化检查的约束（如词数）的提示词来测试指令遵循。GSM-Symbolic 使用模板生成多样化的数学问题。

通常适合这一范式的任务，测试的是数学、逻辑或编程能力。

用模型创建合成数据

如果你想创建合成数据，通常要从若干种子文档开始，它们将充当你的标准答案。这些文档可以是内部的、针对你自身用例的，也可以是网上可获取的高质量内容（如 Wikipedia、Stack Overflow……）。之后你很可能需要把数据切分为自包含意义的单元。

接着，你很可能希望让模型基于你的数据设计问题。为此，你需要选择一个前沿模型，并设计一个非常好的提示词，要求模型从所提供的数据中创建与用例相关的问题。更好的做法是让模型给出它提问所依据的来源。

你也可以用种子提示词作为示例提供给外部模型，让它为你的模型写好提示词，再由你的模型生成新问题——如果你想把合成进行到底 ^^。

完成之后，你可以用另一个模型家族的模型，以你的标准答案 + 问题 + 答案作为输入，让模型裁判进行自动验证。

⚠️
务必确保检查你的数据

无论把所有环节都自动化有多诱人，你都应该在每一步检查你的数据，以确保你的评测是高质量的。评测才是关键所在，你需要使用极其优质的数据。

管理数据污染

一般来说，你应当假定任何在互联网上公开可获取的数据集已经或将会被污染。

缓解措施包括：

  • 在评测集中提供一个金丝雀字符串（如 BigBench 所做）：这是一种特定的字符组合，模型开发者可以在自己的训练集中查找它，一旦出现就表明训练集里包含某个评测
  • 以**加密或门控**的形式提供评测集，使其难以被网络爬虫解析——从而不会意外混入训练集
  • 运行动态基准：基准随时间定期更新，使模型无法“把答案背下来”（但这会让数据集成本更高）
  • 如果你在运行某个基准，尝试事后检测数据污染（例如查看生成结果的困惑度，或设计提示词的对抗版本——不过，没有任何方法能万无一失地检测污染）

不过，正如我们在消融实验部分所看到的，数据集受到污染，并不意味着它在训练过程中就不再有趣、不再有信号。

如果一个模型只能在训练数据上预测得好（而没有潜在地学到更高级的通用模式），就说它过拟合了。在没那么极端的情况下，你仍然想测试模型能否泛化到不在训练集分布内的数据模式（例如，在只见过 reddit 上的毒性内容后，去分类 stack overflow 上的毒性）。

选择提示词

提示词将决定给模型提供多少关于任务的信息，以及这些信息以何种方式呈现给模型。它通常包含以下几个部分：一个可选的任务提示词，用于介绍任务以及输出应遵循的格式；按需附上的上下文（例如来源、图像）；一个问题提示词，即你向模型提出的问题；以及用于多项选择评测的可选选项。

在定义提示词时，你需要意识到，即便语义等价的提示词只发生很小的改动，结果也可能出现相当大的差异，而且提示词格式可能对特定模型有利或不利（见这一节）。

➡️ 缓解办法是：用不同的提示词变体多次重跑评测（但可能成本高昂），或者只跑一次评测，但把一系列提示词格式分配给难度等价的不同样本。

➡️ 你也可以给模型提供示例，帮助它遵循期望的格式（使用少样本示例），而加入连接词总体上对此有帮助。

为你的模型选择推理方法

你需要选定自己要用哪种推理方法。

关于对数似然评测的提醒

使用对数概率适合多项选择问答（MCQA），用来测试模型知识或消歧能力。

  • 优点：
    • 确保所有模型都能获取到正确答案
    • 提供了模型“置信度”（以及校准）的代理指标
    • 评测速度快，尤其是当我们只要求模型预测一个 token 时（A/B/C/D 选项索引，或 Yes/No 等）。
    • 能获得小模型任务表现上的信号
  • 缺点：
    • 会略微高估小模型的表现，因为如果放任其自由生成，它们可能会生成选项范围之外的内容。
    • 有些模型会依据选项被呈现的顺序而偏好特定选项，这可能导致评测结果不具代表性（除非你通过打乱样本顺序重复运行评测 n 次；如果预算允许，为了统计显著性你应当这样做！）
💡
提示：为 MCQA 评测轻松提速

如果你能确保模型在该任务上只需预测一个 token，就能大幅加速你的 MCQA 预测。

这样，你无需运行 number_of_choices 次预测（context + choice 1、context + choice 2 等），只需对 context 运行推理，并计算整个词表上的概率分布（其中会包含你所有单 token 选项），从而得到你关心的对数概率，而且这一步可以一趟完成。

关于生成式评测的提醒

如今大多数评测都是生成式的：在你想要测试流畅度、推理能力，或模型真正回答问题的能力时，使用生成结果非常合适。这也是评测推理模型最相关的方式。

  • 优点：
    • 确实应当与 LLM 生成流畅文本的能力相关，多数情况下也正是人们真正关心的
    • 这是同时评测闭源与开源模型的唯一方式
  • 缺点：
    • 评分可能更难（见下文）
    • 比对对数似然评测更昂贵，尤其是当它们包含采样或推理模型时

评分

如果你看的是对数概率，指标会很简单：你多半会想看某种准确率的变体（最可能的选项恰为最佳选项的频率）。重要的是按序列长度做归一化（按字符、token 或 pmi）。你也可以看困惑度、召回率或 F1 分数。

如果你看的是生成式评测，这里就开始变得非常棘手了，所以下一章专门讲这个！

评测的主要挑战：为自由格式文本评分

给自由格式文本评分很棘手，因为同一个正确答案通常有许多种表达方式，使得通过简单的字符串匹配来判断语义等价变得困难，而输出的变化可能让两个语义完全相同的答案看起来截然不同。回答可能部分正确，或混合了准确与不准确的信息。对于手头的问题，甚至可能不存在唯一的标准答案，例如需要判断连贯性、有用性和风格的任务，这些本质上就是主观且依赖上下文的。

自动评分

不过，当存在标准答案时，你可以使用自动指标，下面看看具体怎么做。

指标

将一段文本与参考文本自动比较的方法，大多基于匹配。

在未包含于模型训练集的数据上做这件事更有意思，因为你想测试它是否能很好地泛化。你不会想要一个只能预测它已经“见过”的文本的模型，那不会太有用！

最简单但最不灵活的基于匹配的指标，是 token 序列的精确匹配。它虽然简单且无歧义，却不提供部分分数——一个只错了一个词的预测，与一个完全错误的预测得分相同。

注意，“精确匹配”被用作一个统称，它也包括字符串的“模糊匹配”：与归一化后比较、在 token 子集上比较（例如只比较前缀）等。

翻译与摘要领域引入了自动指标，通过序列中 n-gram 的重叠来比较相似度。BLEU（Bilingual Evaluation Understudy）衡量与参考译文的 n-gram 重叠，尽管它偏向较短的译文，且在句子层面上与人类判断的相关性很差，但仍被广泛使用（尤其需要注意的是，对于语义等价但写法与参考不同的预测，它效果不佳）。ROUGE 做类似的事，但更侧重面向召回率的 n-gram 重叠。它们的简化版本是 TER（translation error rate，翻译错误率），即从预测改到正确参考所需的编辑次数（类似于编辑距离）。 最后，你还会看到基于模型的指标，使用嵌入距离来衡量相似度，例如 BLEURT（它使用基于 BERT 的学习表示，这些表示在 WMT 的人类判断上训练；相比 n-gram 方法能提供更好的语义理解，但为了达到最佳性能需要下载模型并进行任务特定的微调）。 我在这里介绍的是最知名的指标，但所有这些指标都有变体和扩展，仅举几例：CorpusBLEU、GLEU、MAUVE、METEOR。

一旦你得到每个样本的准确率分数，就可以用几种方式在整个数据集上聚合它。一般来说，人们会对结果取平均，但你可以根据自己的需求做更复杂的事情。（有些指标自带聚合方式，例如 CorpusBLEU。）

如果你的分数是二值的，就看精确率（当假阳性代价高昂时至关重要）、召回率（当漏掉阳性结果代价高昂时至关重要）、F1（平衡精确率与召回率，适合不平衡数据），或 MCC（马修斯相关系数，通过考虑混淆矩阵的所有元素，能很好地处理不平衡数据集）。 如果你的分数是连续值（虽然可能性较小），可以用均方误差（惩罚大误差，但对离群点权重很高）或平均绝对误差（比 MSE 更均衡）。

如果你假设数据应遵循某个特定的线性回归模型（例如你在研究模型校准），可以看 R² 之类的度量，或 Pearson（用于线性关系，假设正态性）、Spearman（用于单调关系，不假设正态性）等相关系数。不过，这有点超出本文范围。

更一般地说，在选择指标及其聚合方式时，需要记住你的任务真正关心的是什么。在某些领域（例如医疗、面向公众交互的聊天机器人），你不想衡量平均表现，而是需要一种方式来评估你能得到的最差表现（输出在医疗质量上的表现、毒性等）。

使用自动化指标的优缺点

自动化基准有以下优点：

  • 一致性与可复现性：你可以在同一个模型上把同一个自动化基准跑 10 次，会得到相同的结果（硬件差异或模型固有的随机性除外）。这意味着你可以轻松地为给定任务创建公平的模型排名。
  • 以有限成本扩展规模：它们是当前评测模型最便宜的方式之一。
  • 可理解性：大多数自动化指标都很容易理解。

不过，它们在更复杂的任务上用途有限：自动指标要么要求你有一个完美、唯一且无歧义的参考/标准答案，就像那些表现易于定义和评估的任务（例如毒性分类、只有一个答案的知识问答）。另一方面，更复杂的能力更难分解成一个简单而唯一的答案。

归一化如果设计不当，很容易变得不公平，但总的来说，它们仍然有助于在任务层面提供信号。

它们对于评测通过思维链或推理生成的预测也很重要，因为你需要从输出中去掉推理轨迹（它不属于最终答案），才能得到真正的答案。

采样

当模型生成输出时，多次采样并聚合结果，能比单次贪心生成提供更稳健的信号。 这对复杂推理任务尤其重要——模型可能通过不同路径得到正确答案。

常见的基于采样的指标有：

  • n 个样本上的 pass@k：给定 n 个生成样本，衡量其中是否至少有 k 个通过测试。

    你会看到 pass@k 有两种计算方式：简单地算作 pass@k=(c>=k)\text{pass}@k = (c >= k)pass@k=(c>=k)，或用无偏估计量计算：pass@k=1−(n−ck)(nk)\text{pass}@k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}pass@k=1−(kn​)(kn−c​)​，其中 c 是 n 个总样本中正确样本的数量。

  • maj@n（多数投票）：采样 n 次生成，取出现次数最多的答案。这有助于过滤掉偶发的输出，当模型的正确推理路径比其错误更一致时，效果尤其好。常用于数学和推理任务。

  • cot@n（思维链采样）：采样 n 条推理轨迹并对其进行评估。可以与多数投票或 pass@k 结合使用（采样 n 条推理链，抽取最终答案，取多数或设一个阈值）。

  • avg@n（稳定的平均分）：对 n 个样本的分数取平均。与使用“最好”或“最常见”的情况相比，这是更稳定的性能估计。

使用采样评测时，务必始终报告所有采样参数（温度、top-p、k 值），因为它们会显著影响结果。

什么时候可以用采样，什么时候不该用？
  • 用于训练评测/消融实验：❌ 一般应避免采样指标，因为它们昂贵且会引入方差。坚持使用固定随机种子的贪心解码。
  • 用于后训练评测：✅ 采样指标能揭示贪心解码遗漏的能力（尤其是需要推理、数学或代码的更复杂任务）。
  • 推理时：✅ 这些指标有助于估计在推理时多次采样能带来多少提升。当你想研究用测试时计算能把小模型推到多远时，这尤其有用。

不过要记住，采样 k 次会把评测成本乘以 k。对于昂贵的模型或大型数据集，成本会累积得非常快！

函数式评分器

函数式测试不是通过模糊字符串匹配把生成文本与参考比较，而是评估输出是否满足特定的可验证约束。这种方法非常有前景，因为它更灵活，并且允许通过基于规则的生成对测试用例进行“无限”更新（从而减少过拟合）。

IFEval 和 IFBench 是指令遵循评测中这种方法的绝佳例子。它们不问“这段文本是否匹配某个参考答案？”，而是问“这段文本是否满足指令中给出的格式约束？”

例如，指令可能规定：

  • “恰好包含 3 个要点” → 验证输出中恰好有 3 个要点
  • “只把第一句的首字母大写” → 解析并检查大小写模式
  • “至少使用两次 ‘algorithm’ 这个词” → 统计词出现次数
  • “你的回复必须是 JSON 格式，包含键 ‘answer’ 和 ‘reasoning’” → 校验 JSON 结构

每条约束都可以用特定的基于规则的验证器来检查，这使得这类评测比使用模型作为裁判更无歧义、更可解释、更快，而且成本低得多。

这种函数式方法对指令遵循特别有效，但要扩展到其他文本属性则需要创造力。关键在于找出文本中那些可以通过程序而非语义比较来验证的方面。

功能测试的思路来自代码评测，在代码评测中，通过单元测试做功能测试是标准做法（检查生成的代码对给定输入是否产生正确输出）。

用人类

人工评测就是请人类为预测结果打分。

人工评测非常有意思，因为它具备灵活性（只要把你评测的东西定义得足够清楚，几乎任何东西都能拿到分数！）、天然的未污染性（如果由人类编写新问题来测试你的系统，这些问题有望不出现在你的训练数据里），以及与人类偏好的良好相关性——原因显而易见。

不过，在让人类参与评测时，你需要确保标注者足够多样，以便结果具有泛化性。

在人类参与的情况下评测模型，有几种不同的做法。

直觉检查（vibe-checks）指的是社区成员个人进行的手动评测，通常针对未公开的提示词，目的是获得模型在其偏好的用例上表现如何的整体“感觉”。（我也见过用“金丝雀测试”一词来指代这种做法，借用了煤矿中高信号金丝雀的比喻。）这些用例可以是最令人兴奋的，也可以是最平淡乏味的——举几个我在 Reddit 上见过的例子，涵盖德语法律问题、编程、工具使用、情色内容写作质量等。它们常被发布在论坛或社交媒体上，大多只构成轶事性证据，并且往往对确认偏误高度敏感（换句话说，人们往往会找到他们想找的东西）。

利用社区反馈来建立大规模的模型排名，就是我们所说的竞技场（arena）。一个广为人知的例子是 LMSYS chatbot arena，社区用户在其中与模型聊天，直到他们发现其中一个比另一个更好。投票随后被聚合成 Elo 排名（一种基于对局的排名），以此选出哪个模型“最好”。这种做法明显的问题在于主观性很高——仅凭宽泛的指南，很难让众多社区成员给出一致评分，尤其是标注者的偏好往往受文化约束（例如，不同的人偏好不同的讨论话题）。人们可以寄希望于投票规模之大能通过“群体智慧”效应抹平这种影响（这一效应由一位名叫高尔顿的统计学家发现，他观察到，个人为估计某个数值——比如一头猪的重量——给出的答案，可以被建模为以真实答案为中枢的概率分布）。

最后一种做法是系统性标注：你为付费挑选出来的标注者提供极其具体的指南，以尽可能消除主观性偏见（这是大多数数据标注公司采用的做法）。但它的成本会迅速变得极高，因为对于每一个你想评测的新模型，你都得持续地以非自动化的方式做评测；而且它仍然可能受制于人类偏见（这项研究表明，身份不同的人对模型回答毒性的评分往往差异很大）。

直觉检查是一个特别适合你自己用例的起点，因为你会用与你相关的内容来测试模型。随性人工评测的优点在于成本低，并且让你能以一种基本不受限的方式利用用户的创造力，从而发现有趣的边缘情况。不过，它们也容易存在盲区。

例如，科学界曾就 LLM 是否能画独角兽有过争论。一年之后，看起来大多数模型都能画了！

一旦你想扩展到用付费标注者进行更系统的评测，你会发现主要有 3 种做法。如果你还没有数据集，但想探索一组能力，你给人类一个任务和评分指南（例如 试着让这两个模型的输出都包含毒性语言；模型若输出毒性语言得 0 分，没有则得 1 分。），并让他们能访问一个（或多个）可以交互的模型，然后请他们给出分数和理由。如果你已经有数据集（例如一组你希望模型永远不要回答的提示词，比如出于安全目的），你预先用这些提示词提示模型，然后把提示词、输出和评分指南交给人类。如果你已经有数据集和分数，你可以请人类通过做错误标注来审查你的评测方法（它也可以用作上述类别中的评分系统）。这是测试新评测系统非常重要的一步，但严格来说它属于评测一个评测，因此略微超出了本文的范围。

系统性人工评测的优点，尤其是在使用付费标注者时，在于你能获得契合自己用例的高质量私有数据（特别是当你依赖内部标注者时），而且这些数据大多是可解释的（模型得到的分数可以由给出分数的人类解释）。 然而，它成本更高（尤其是你很可能需要多轮标注来调整指南），而且扩展性不好。

不过总体而言，人工评测存在若干众所周知的偏见，基于第一印象、语气、与标注者价值观的一致性等，见下图。

这些偏见并不出人意料，但必须加以考虑：并非所有用例都应依赖廉价的众包标注者——任何要求事实性的任务（如写代码、评测模型知识等）都应加入另一种更稳健的评测类型来补全基准（专家、适用的自动指标等）。

用裁判模型

为了降低人工标注者的成本，一些人开始研究用模型或衍生产物（最好是与人类偏好对齐的）来评估模型的输出。

这种做法并不新鲜，2019 年就有利用模型嵌入衡量摘要质量的技术。

裁判模型就是用来评估其他神经网络输出的神经网络。多数情况下，它们评估的是文本生成结果。

评分有两种做法：使用通用、高能力的模型，或使用小型专家模型——后者专门在偏好数据上训练以做区分（可以想象成“垃圾邮件过滤器”，只不过过滤的是毒性之类的东西）。在前一种情况下，用 LLM 当裁判时，你给它一个提示词，说明如何给模型打分（例如 Score the fluency from 0 to 5, 0 being completely un-understandable, ...）。

模型裁判可以对复杂而细微的属性给文本打分。 例如，预测与参考答案之间的精确匹配可以让你检验模型是否预测出正确的事实或数字，但评估更开放的经验性能力（如流畅度、诗歌质量，或对输入的忠实度）需要更复杂的评估器。

它们主要用于 3 类任务：

  • 为模型生成结果打分：在给定的量表上，评估文本的某项属性（流畅度、毒性、连贯性、说服力等）。
  • 成对打分：比较一对模型输出，针对给定属性挑出更好的文本
  • 计算相似度：模型输出与参考文本之间的相似度
在本文中，我目前会聚焦于 LLM + 提示词的做法，但你绝对应该去看看分类器裁判（classifier judges）是如何工作的，因为我认为它相当稳健，且能很好地适配多种用例；也值得看看最近提出、前景可期的“以奖励模型为裁判”的做法（见这份技术报告，我们这里有一个小页面）

使用裁判 LLM 的优缺点

支持 LLM 裁判的人一直声称，它们能提供更好的：

  • 与人类相比的客观性：它们以客观且可复现的方式自动化经验性判断（理论上如此——在我看来，它们引入的微妙偏见超过了其价值）
  • 规模与可复现性：它们比人类标注者更具扩展性，从而能在大量数据上复现打分（前提是你控制温度）。
  • 成本：它们实例化成本低，因为不需要训练新模型，只需依赖良好的提示和一个现有的高质量 LLM。它们也比付钱给真正的人类标注者更便宜（资本主义……）。

在我看来，正确使用 LLM 裁判极其棘手，而且在关键用例上很容易被蒙骗：

  • LLM 裁判看起来客观，但它们有许多隐藏偏见，而且这些偏见比人类的偏见更难察觉，因为我们不会那么主动地去寻找它们（见下文）。此外，可以通过以特定且统计上稳健的方式设计调查问题来减少人类偏见（社会学对此已研究了大约一个世纪），而 LLM 提示在这方面还不够稳健。有人把用 LLM 评测 LLM 比作制造回音室效应，会微妙地强化偏见。
  • 它们确实可扩展，但会助推产生海量数据，而这些数据本身需要被检查以确保质量（例如，你可以通过让 LLM 裁判生成思维轨迹、或围绕其数据做推理来提升裁判质量，但这会产生更多需要分析的新人工数据）
  • 它们实例化成本确实低，但在你的具体用例上，效果不如花钱请真正的专家标注者。

因此这一节有点长，因为你需要充分了解把模型用作裁判的局限：很多人盲目地一头扎进这种做法，因为它看起来比真正与人类合作或设计新指标更省事，但最终得到的是难以解释、且带有难以剥离的棘手偏见的数据。

我个人对用模型做裁判最大的不满在于，它们会在答案选择中引入非常微妙且无法解释的偏见。我感觉，就像遗传学研究中过度杂交最终会得到功能失调的动植物一样，用 LLM 来筛选和训练 LLM，同样很可能引入细微变化，而这些变化在几代之后会产生更大的连锁反应。我认为，更小、更专用的裁判模型（例如毒性分类器）不太可能出现这类偏见，但这仍有待严格的测试与证明。

使用小型专用 LLM 裁判模型

你也可以选择使用小型专用的 LLM 裁判。它们通常只有几十亿参数，能在大多数近期的消费级硬件上本地运行，同时可以用指令数据从零训练或微调。你通常需要遵循它们特定的提示词格式。

截至 2024 年，一些已有的模型包括 Flow-Judge-v0.1（权重），38 亿参数，是在合成偏好数据集上微调的 Phi-3.5-mini-instruct；Prometheus（权重、论文），130 亿参数，是在合成偏好数据集上从零训练的模型；以及 JudgeLM（论文），70 亿到 330 亿参数，是在用多种模型生成的合成偏好数据集上从零训练的模型。现在肯定有更新的替代方案！

训练自己的裁判 你也可以选择训练或微调自己的 LLM 裁判。（除非你处在非常小众的领域，否则我会避免这样做。）

如果走这条路，你首先需要为感兴趣的任务收集偏好数据，这些数据可以来自

  • 现有的人类偏好数据集
  • 由模型生成的偏好数据（你可以按照上面那些小型模型裁判论文的数据部分来生成，也可以直接获取，例如从 Prometheus 的偏好和反馈数据集中获取）。

然后你需要决定：是从一个小模型开始从零训练，还是从现有模型出发——你可以把它蒸馏成一个新的更小的模型，或做量化，然后用上述数据微调（如果模型很大而你的训练算力很低，可以使用 peft 或适配器权重）。

显然，从奖励模型出发比从指令模型出发效果更好

设计你的评测提示词

选定模型后，你需要为你的任务确定尽可能最好的提示词。

📝
提示词设计指南

清楚地描述手头的任务：

  • 你的任务是做 X。
  • 你会拿到 Y。

清楚地说明评测标准，必要时给出详细的评分体系：

  • 你应就属性 Z 按 1 - 5 打分，其中 1 表示……
  • 你应评估样本 Y 中是否存在属性 Z。若……则属性 Z 存在

给出一些额外的“推理”步骤：

  • 要判断这项任务，你必须先仔细阅读样本 Y 以找出……，然后……

明确要求的输出格式（增加字段有助于保持一致性）

  • 你的答案应以 JSON 给出，格式如下 {“Score”: Your score, “Reasoning”: The reasoning which led you to this score}

你完全可以、也应该从 MixEval 或 MTBench 的提示词模板中汲取灵感。

⚠️
用模型做裁判时要记住的事

成对比较与人类偏好的相关性更好，优于打分，而且通常更稳健。

如果你确实想要一个分数，请使用整数刻度，并确保详细解释每个分数代表什么，或者使用加总式提示词（回答具备这一特征得 1 分，若……再加 1 分等）

每项能力用一个提示词来打分，往往能得到更好、更稳健的结果

你也可以用下面这些可能更昂贵的技术来提升准确率：

  • 少样本示例：和许多其他任务一样，提供示例有助于模型推理。不过这会增加你的上下文长度。
  • 参考：如果存在参考答案，你也可以把它加进提示词，从而提高准确率
  • CoT：能提升较老一代模型的准确率，前提是你要求模型在给出分数之前输出其思维链（在这里也观察到了这一点）
  • 多轮分析：可以提升事实性错误检测的效果
  • 使用评审团（多个裁判，取它们答案的聚合）：效果优于使用单个模型。用许多较小的模型代替一个昂贵的大模型，可以显著降低成本。你也可以尝试用同一个模型配合不同的温度。
  • 出乎意料的是，社区发现给提示词加上筹码（answer correctly and you'll get a kitten）能提升正确率。这一条效果因人而异，按需调整。

如果你在做关键任务（例如医疗领域），务必使用从人文学科移植过来的方法：1）计算标注者间一致性指标，确保评测者尽可能无偏；2）在设计评分网格时采用规范的问卷设计方法，以减轻偏见。不过，大多数人其实并不真的想要一个可复现、高质量、无偏的评测，只要能用还过得去的提示词做快速粗糙的评测，他们就满意了。（这本身没问题！只是取决于要承担的后果。）

评测你的评测器

在生产环境或大规模使用 LLM 裁判之前，你需要针对自己的任务评估它的质量，确认它的分数对你确实相关且有用。

如果你的裁判输出二分类结果，这件事会更容易，因为你可以使用可解释的分类指标（准确率/召回率/精确率）。如果它输出的是某个刻度上的分数，那么估计其与参考之间相关性的质量会困难得多。模型在刻度上做预测是出了名的差。

因此，选定模型裁判及其提示词之后，你需要做以下几件事。

  1. 选定基线 你需要把你的评测器判断与某个基线做比较：基线可以是人工标注、另一个你确知在该任务上质量不错的裁判模型的输出、标准答案、同一模型配另一个提示词的输出，等等。
🎯
基线重质不重量

你不需要很多基线样本（50 个就够了），但它们必须：

  • 有代表性：覆盖你任务的完整范围
  • 有区分度：包含边缘情况和有挑战性的例子
  • 高质量：使用你能拿到的最好的参考数据
  1. 选定指标 你的指标将用于把裁判的评测结果与你的参考做比较。

一般来说，如果你的模型输出二分类结果或做成对比较，这个比较会容易得多，因为你可以计算准确率（成对比较），或精确率和召回率（二分类），这些指标都非常容易解释。

比较分数与人类打分或模型打分的相关性则更难。要更详细地理解原因，我建议你读这篇关于该主题的博客章节。

一般来说，如果你对何时该选什么指标有点迷茫（在模型、指标等方面），也可以看看上面同一篇博客里这张很有意思的图 ⭐。

  1. 评测你的评测器 这一步，你只需用你的模型和它的提示词去评测你的测试样本！拿到评测结果后，用上面的指标和参考为你的评测计算一个分数。

你需要决定可接受的阈值。取决于任务难度，如果你做成对比较，可以以 80% 到 95% 的准确率为目标。至于相关性（如果你用分数），文献里的人似乎对与参考的 0.8 皮尔逊相关感到满意。不过我也见过一些论文声称 0.3 就表示与人类标注者有良好相关性（^^“）所以因人而异。

技巧与提示

⚠️
缓解 LLM 裁判的已知偏见

我们在本节引言中讨论了 LLM 裁判的若干偏见。下面看看该如何缓解它们。

缺乏内部一致性： ➡️ 你可以对裁判做自一致性提示，多次提示它并保留多数输出，以此缓解

自我偏好： ➡️ 你可以使用评审团来缓解

对输入扰动不敏感： ➡️ 要求模型在给出分数之前解释其推理 ➡️ 或者在提示词中给出连贯的评分刻度。

位置偏见： ➡️ 随机交换答案位置 ➡️ 计算所有可能选项的对数概率，得到归一化后的答案

冗长偏见（或长度偏见）： ➡️ 你可以在评分时考虑答案的长度差异来缓解

格式偏见： ➡️ 你可以关注训练时的提示词格式（如果模型经过指令微调），并确保遵循它，以此缓解

为 LLM 裁判选对任务

LLM 评测器：

  • 通常不擅长识别幻觉，尤其是所谓部分幻觉（看起来接近标准答案，实际却略有不同）（见这篇和这篇）
  • 在摘要（这里也有）、忠实性任务上与人类标注者的相关性从低到还算可以，并且在更广的一系列任务上并不总是与人类判断相关

那奖励模型呢？

奖励模型学习根据人类对给定提示词/补全对的标注来预测分数。最终目标是让它们的预测与人类偏好对齐。 训练完成后，这些模型便可用作奖励函数，作为人类判断的代理，来改进其他模型。

最常见的奖励模型类型是 Bradley-Terry 模型，它输出单一的成对分数，形式如下：

p(completion b is better than completion a)=sigmoid(scoreb−scorea)p(\text{completion b is better than completion a}) = \text{sigmoid}(\text{score}_b - \text{score}_a)p(completion b is better than completion a)=sigmoid(scoreb​−scorea​)

该模型仅使用补全之间的成对比较进行训练，这类数据比分数更容易收集，但它只能比较针对同一个提示词的若干补全，无法跨提示词比较补全。

其他模型在这一方法上做了扩展，用来预测某个补全优于另一个补全的更细致的概率（示例）。

这使得它们（理论上）能够判断补全之间的细微差异，代价是无法轻松地为同一测试集保存并比较跨提示词的众多不同分数。此外，比较过长的补全时，上下文长度和内存限制也可能成为问题。

一些奖励模型（例如 SteerLM）输出绝对分数，可以直接用于评测补全，无需成对比较。这类模型在评测中更易于使用，但收集数据也更难，因为在人类偏好中绝对分数往往不如成对分数稳定。

最近，也有研究提出了同时输出绝对分数和相对分数的模型，例如 HelpSteer2-Preference 和 ArmoRM。

如何使用奖励模型进行评测？

给定一个提示词数据集，我们可以用语言模型生成补全，并让奖励模型为其打分。

对于给出绝对分数的模型，可以把得到的分数取平均，作为合理的汇总分数。

然而，在更常见的相对分数情形下，平均奖励会被离群值（少数极好或极差的补全）带偏，因为不同提示词的奖励尺度可能天然不同（有些提示词比其他提示词难得多或容易得多）。

对于相对分数，不要直接对原始奖励取平均——离群值以及提示词难度尺度之间的差异会使结果产生偏差。应改用相对于参考结果的胜率或胜出概率。

因此，我们可以使用

  • 胜率：取一组参考补全，计算模型补全中排名高于参考补全的比例。它的粒度稍细。
  • 胜出概率：补全优于参考补全的平均概率，可提供更细粒度且平滑变化的信号。
奖励模型的优缺点

奖励模型通常：

  • 非常快：得到分数只需要对一个相对较小的模型做一次前向传播（因为我们只得到一个分数，而不像 LLM 裁判那样得到长文本）
  • 确定性：同样的前向传播会复现同样的分数
  • 不太会受位置偏见影响：由于大多数模型只接收一个补全，顺序无法影响它们。对于成对模型，位置偏见通常也很小，只要训练数据在包含”第一个回答最优”和”第二个回答最优”两方面保持平衡。
  • 无需提示工程：因为模型会根据其训练所用的偏好数据，直接从一个或两个补全中输出分数。

另一方面，它们：

  • 需要专门微调：这一步成本可能较高，而且尽管它们从基座模型继承了许多能力，在训练分布之外的任务上仍可能表现不佳。
  • 在强化学习和评测中同时使用时效率会下降（或在训练数据与奖励模型训练数据相似的数据集上使用直接对齐算法时），因为语言模型可能过拟合奖励模型的偏好。

约束模型输出

在许多情况下，我们可能希望模型输出遵循非常特定格式的预测，以简化评测。

使用提示词

最简单的做法是添加任务提示词，其中包含关于模型应如何作答的非常具体的指令（Provide numerical answers in digits.、Use no abbreviation. 等）。

这未必总能奏效，但对能力强的模型应该足够好。例如，我们在 GAIA 论文中采用的就是这种方法。

少样本与上下文学习

下一种方法是通过所谓的”上下文学习”来约束模型。在提示词中提供示例（即 few-shot prompting），会让模型在回答实际样本时，隐含地偏向于遵循重复出现的提示词形式。

直到 2023 年底，这种方法总体上效果都相当不错！

然而，随着指令微调方法的广泛采用，以及在模型预训练后期（持续预训练）加入指令数据，较新的模型已经偏向特定的输出格式（这里称之为在测试任务上训练，而我称之为过拟合提示词格式）。推理模型也因为推理轨迹而与少样本示例配合得不太好。

对于上下文规模较小的旧模型，这种方法也可能受限，因为有些少样本示例无法放进上下文窗口。

结构化文本生成

结构化文本生成会把输出约束为遵循给定路径，例如由语法或正则表达式定义的路径。outlines 库使用有限状态机实现这一点，非常巧妙。（还存在其他方法，例如在生成 JSON 时使用交错生成，但有限状态机是我最喜欢的一种。）

想进一步了解使用结构化生成时会发生什么，可以看看我们合写的博客：结构化生成能降低评测中的提示词方差，使结果和排名更稳定。你也可以浏览 outlines 的整体博客，了解与结构化生成相关的有趣实现和观察。

不过，最近的一些研究似乎表明，结构化生成会把先验推离期望的概率分布太远，从而在某些任务（如推理）上降低模型表现。

评测中被遗忘的孩子

统计有效性

在报告评测结果时，除了点估计，还必须给出置信区间。

这些基于原始分数的置信区间，可以通过分数的标准差或自助法（bootstrapping）得到——对自动指标来说，这相对简单——对模型裁判来说，一篇近期论文建议用估计量做偏差校正。对基于人类的评测，你应该报告一致性。

你也可以用提示词变体来计算这些区间：用略微不同的方式问同样的问题，或者用不同的提示词格式在同一批样本上重新运行。

成本与效率

在设计和报告评测结果时，我们需要开始集体报告结果与模型运行成本之间的关系！一个需要 10 分钟思考和 10K token 才能答出 10 + 1 的推理模型（因为它决定就二进制与十进制算术展开一整段跑题论述），其效率远低于一个只用少数几个 token 就答出 30 的小模型。

我们建议报告以下内容：

  • token 消耗：报告评测期间使用的输出 token 总数。这对估计效率尤为重要，而且它会影响以模型作为裁判的评测的成本。token 数量直接影响金钱成本，并帮助他人估计算力需求。金钱成本也可以是效率的一个良好代理指标。
在比较不同评测方法时，这些成本指标也可能很关键。例如，用一个强大的 LLM 作为裁判可能比自动指标提供更好的信号，但 100 倍的成本增长可能并非对所有用例都值得。同样，基于采样的指标（pass@k、maj@n）会让成本随样本数量成倍增加，这应当与它们带来的信号提升相权衡。
  • 时间：记录模型完成评测所需的推理时间。这既包括实际推理时间，也包括 API 速率限制带来的任何额外开销。这对任何对时间敏感的应用（比如 GAIA2 中的某些智能体工具使用）尤为重要。

最后但同样重要的是，考虑到地球上可用资源的整体状况，报告你所运行的模型的环境足迹正变得越来越重要。这包括训练产生的碳排放和推理时的能源消耗，而这些取决于模型规模、硬件（如果你知道的话）和生成的 token 数。一些更小或量化的模型能达到非常有意思的性能与消耗之比

结论

评测既是一门艺术，也是一门科学。我们探讨了 2025 年 LLM 评测的全景——从理解我们为什么要评测模型，以及分词和推理的基本机制，到在不断演化的基准生态中穿行，最后到为你自己的用例创建评测。

我希望你能记住的几个要点是：

批判性地思考你在测量什么。 评测是能力的代理指标，因此基准上的高分并不能保证真实世界中的表现。不同的评测方法（自动指标、人类裁判或模型裁判）各有其偏见、局限和取舍。

让评测与你的目标匹配。 你在训练期间做消融实验吗？那就使用快速、可靠、即使在小模型上也有强信号的基准。要比较最终模型以做选择？那就聚焦于更难、未被污染、能考察整体能力的数据集。要为特定用例构建？那就创建能反映你的问题和数据的自定义评测。

可复现性需要关注细节。 提示词、分词、归一化、模板或随机种子的微小差异都可能让分数波动几个点。报告结果时，要对你采用的方法保持透明。尝试复现结果时，要预料到即使你试图控制每一个变量，精确复现也会极其困难。

优先选择可解释的评测方法。 在可能的情况下，应选择函数式测试和基于规则的验证器，而不是模型裁判。能够被理解和调试的评测会提供更清晰、更可操作的洞见……而且你的评测越可解释，你就越能改进你的模型！

评测永远不会结束。 随着模型改进，基准会饱和。随着训练数据增长，数据污染更可能发生。随着用例演化，新的能力需要被测量。评测是一场持续的战斗！

最后：我们构建的模型有多好，取决于我们测量关键事物的能力。感谢阅读！
