### 数据集

<a id="using-existing-data"></a>

#### 使用现有数据
你可以按原样使用现有数据集，并更改相关的提示或指标（正如为适配新的提示方法而对较早的评测所做的那样），但你也可以聚合数据集。

当你想评测某项特定能力、而单一基准未能很好地覆盖它时，数据集聚合是个好办法。与其从零开始，你可以把多个现有数据集的样本组合起来，构建一套有针对性的评测集。例如，“Measuring AGI”论文的作者最近就这么做，试图创建一个新的“AGI 评测”数据集。

聚合数据集时，要注意以下问题：
- 它们是否包含冗余数据（大多数数学数据集都是对同一批初始问题的改写或聚合）
- 你需要在各来源之间保持均衡的代表性（你可能不希望某个数据集占据主导并扭曲你的评测）——这也决定了分数是按全部样本聚合，还是按各个子集聚合
- 格式与难度级别是否兼容（通常来说，构建统一数据集时，要小心混合那些需要采样和不需要采样的样本）。

<Sidenote>示例：MMLU、Big-Bench（数百个多样化任务）以及 HELM（组合多个现有基准做整体评测）</Sidenote>

EpochAI（2025）的新研究展示了如何[在单一框架下最好地聚合基准](https://epoch.ai/blog/a-rosetta-stone-for-ai-benchmarks)，使聚合后的数据集整体上更难，也更不容易饱和。

<a id="creating-a-dataset-synthetically"></a>

#### 合成创建数据集
**使用基于规则的技术**

如果你的任务允许，使用程序化生成的基准是获得近乎无限样本并避开数据污染的好办法！它们能以算法方式生成无限多全新的测试用例，同时控制难度并支持自动验证，确保模型在训练中没见过这些样例。

一些例子可以看 [NPHardEval](https://arxiv.org/abs/2312.14890)、[DyVal](https://arxiv.org/abs/2309.17167)、[MuSR](https://arxiv.org/abs/2310.16049)、[BabiQA](https://arxiv.org/abs/1502.05698)、[ZebraLogic](https://arxiv.org/pdf/2502.01100)、IFEval 或 GSMTemplate 等。**NPHardEval** 生成以复杂度为基础的任务，比如带自动验证的图问题，并每月刷新以降低过拟合。**MuSR** 使用神经符号生成来创建复杂的推理实例，比如 1000 词的谋杀谜案。**ZebraLogic** 通过生成解并用 SAT 求解器迭代最小化线索，以算法方式产出逻辑网格谜题。**BabiQA** 模拟实体执行一连串动作。**IFEval** 用 500 多个包含可程序化检查的约束（如词数）的提示词来测试指令遵循。**GSM-Symbolic** 使用模板生成多样化的数学问题。

通常适合这一范式的任务，测试的是数学、逻辑或编程能力。

**用模型创建合成数据**

如果你想创建合成数据，通常要从若干种子文档开始，它们将充当你的标准答案。这些文档可以是内部的、针对你自身用例的，也可以是网上可获取的高质量内容（如 Wikipedia、Stack Overflow……）。之后你很可能需要把数据切分为自包含意义的单元。

接着，你很可能希望让模型基于你的数据设计问题。为此，你需要选择一个前沿模型，并设计一个非常好的提示词，要求模型从所提供的数据中创建与用例相关的问题。更好的做法是让模型给出它提问所依据的来源。

你也可以用种子提示词作为示例提供给外部模型，让它为你的模型写好提示词，再由你的模型生成新问题——如果你想把合成进行到底 ^^。

完成之后，你可以用另一个模型家族的模型，以你的标准答案 + 问题 + 答案作为输入，让模型裁判进行自动验证。

<Note title="务必确保检查你的数据" emoji="⚠️" variant="warning">
无论把所有环节都自动化有多诱人，你都应该在每一步检查你的数据，以确保你的评测是高质量的。评测才是关键所在，你需要使用极其优质的数据。
</Note>

<a id="managing-contamination"></a>

#### 管理数据污染
一般来说，你应当假定任何在互联网上公开可获取的数据集已经或将会被污染。

缓解措施包括：
- 在评测集中提供一个**金丝雀字符串**（如 [BigBench](https://github.com/google/BIG-bench) 所做）：这是一种特定的字符组合，模型开发者可以在自己的训练集中查找它，一旦出现就表明训练集里包含某个评测
- 以**[加密](https://arxiv.org/abs/2309.16575)或[门控](https://huggingface.co/datasets/Idavidrein/gpqa)**的形式提供评测集，使其难以被网络爬虫解析——从而不会意外混入训练集
- 运行[动态基准](https://arxiv.org/abs/2104.14337)：基准随时间定期更新，使模型无法“把答案背下来”（但这会让数据集成本更高）
- 如果你在运行某个基准，尝试事后[检测数据污染](https://arxiv.org/abs/2311.06233)（例如查看生成结果的困惑度，或设计提示词的对抗版本——不过，没有任何方法能万无一失地检测污染）

不过，正如我们在消融实验部分所看到的，数据集受到污染，并不意味着它在训练过程中就不再有趣、不再有信号。

<Note>
如果一个模型只能在训练数据上预测得好（而没有潜在地学到更高级的通用模式），就说它**过拟合**了。在没那么极端的情况下，你仍然想测试模型能否泛化到不在训练集分布内的数据模式（例如，在只见过 reddit 上的毒性内容后，去分类 stack overflow 上的毒性）。
</Note>


<a id="choosing-a-prompt"></a>

### 选择提示词
提示词将决定给模型提供多少关于任务的信息，以及这些信息以何种方式呈现给模型。它通常包含以下几个部分：一个可选的**任务提示词**，用于介绍任务以及输出应遵循的格式；按需附上的**上下文**（例如来源、图像）；一个**问题提示词**，即你向模型提出的问题；以及用于多项选择评测的可选选项。

在定义提示词时，你需要意识到，即便语义等价的提示词只发生很小的改动，结果也可能出现相当大的差异，而且提示词格式可能对特定模型有利或不利（见[这一节](https://huggingface.co/spaces/OpenEvals/evaluation-guidebook#different-prompt)）。

➡️ 缓解办法是：用不同的提示词变体多次重跑评测（但可能成本高昂），或者只跑一次评测，但把一系列提示词格式分配给难度等价的不同样本。

➡️ 你也可以给模型提供示例，帮助它遵循期望的格式（使用少样本示例），而加入连接词总体上对此有帮助。

<a id="choosing-an-inference-method-for-your-model"></a>

### 为你的模型选择推理方法
你需要选定自己要用哪种推理方法。

<Note title="关于对数似然评测的提醒">
使用对数概率适合多项选择问答（MCQA），用来测试模型知识或消歧能力。
- 优点：
	- 确保所有模型都能获取到正确答案
	- 提供了模型“置信度”（以及校准）的代理指标
	- 评测速度快，尤其是当我们只要求模型预测一个 token 时（A/B/C/D 选项索引，或 Yes/No 等）。
	- 能获得小模型任务表现上的信号
- 缺点：
	- 会略微高估小模型的表现，因为如果放任其自由生成，它们可能会生成选项范围之外的内容。
	- 有些模型会[依据选项被呈现的顺序而偏好特定选项](https://arxiv.org/abs/2309.03882)，这可能导致评测结果不具代表性（除非你通过打乱样本顺序重复运行评测 n 次；如果预算允许，为了统计显著性你应当这样做！）
</Note>

<Note title="提示：为 MCQA 评测轻松提速" emoji="💡">
如果你能确保模型在该任务上只需预测一个 token，就能大幅加速你的 MCQA 预测。

这样，你无需运行 `number_of_choices` 次预测（`context + choice 1`、`context + choice 2` 等），只需对 `context` 运行推理，并计算整个词表上的概率分布（其中会包含你所有单 token 选项），从而得到你关心的对数概率，而且这一步可以一趟完成。
</Note>

<Note title="关于生成式评测的提醒">
如今大多数评测都是生成式的：在你想要测试流畅度、推理能力，或模型真正回答问题的能力时，使用生成结果非常合适。这也是评测推理模型最相关的方式。

- 优点：
	- 确实应当与 LLM 生成流畅文本的能力相关，多数情况下也正是人们真正关心的
	- 这是同时评测闭源与开源模型的唯一方式
- 缺点：
	- 评分可能更难（见下文）
	- 比对对数似然评测更昂贵，尤其是当它们包含采样或推理模型时
</Note>

<a id="scoring"></a>

### 评分

如果你看的是**对数概率**，指标会很简单：你多半会想看某种准确率的变体（最可能的选项恰为最佳选项的频率）。重要的是按序列长度做归一化（按字符、token 或 pmi）。你也可以看困惑度、召回率或 F1 分数。

如果你看的是**生成式**评测，这里就开始变得非常棘手了，所以下一章专门讲这个！

<a id="evaluations-main-challenge-scoring-free-form-text"></a>

## 评测的主要挑战：为自由格式文本评分

给自由格式文本评分很棘手，因为同一个正确答案通常有许多种表达方式，使得通过简单的字符串匹配来判断语义等价变得困难，而输出的变化可能让两个语义完全相同的答案看起来截然不同。回答可能部分正确，或混合了准确与不准确的信息。对于手头的问题，甚至可能不存在唯一的标准答案，例如需要判断连贯性、有用性和风格的任务，这些本质上就是主观且依赖上下文的。

<a id="automatically"></a>

### 自动评分

不过，当存在标准答案时，你可以使用自动指标，下面看看具体怎么做。

<a id="metrics"></a>

#### 指标
将一段文本与参考文本自动比较的方法，大多基于匹配。

<Sidenote>在未包含于模型训练集的数据上做这件事更有意思，因为你想测试它是否能很好地**泛化**。你不会想要一个只能预测它已经“见过”的文本的模型，那不会太有用！</Sidenote>

最简单但最不灵活的基于匹配的指标，是 token 序列的**精确匹配**。它虽然简单且无歧义，却不提供部分分数——一个只错了一个词的预测，与一个完全错误的预测得分相同。<Sidenote>注意，“精确匹配”被用作一个统称，它也包括字符串的“模糊匹配”：与归一化后比较、在 token 子集上比较（例如只比较前缀）等。</Sidenote>

翻译与摘要领域引入了自动指标，通过序列中 n-gram 的重叠来比较相似度。**BLEU**（Bilingual Evaluation Understudy）衡量与参考译文的 n-gram 重叠，尽管它偏向较短的译文，且在句子层面上与人类判断的相关性很差，但仍被广泛使用（尤其需要注意的是，对于语义等价但写法与参考不同的预测，它效果不佳）。**ROUGE** 做类似的事，但更侧重面向召回率的 n-gram 重叠。它们的简化版本是 **TER**（translation error rate，翻译错误率），即从预测改到正确参考所需的编辑次数（类似于编辑距离）。
最后，你还会看到基于模型的指标，使用嵌入距离来衡量相似度，例如 **BLEURT**（它使用基于 BERT 的学习表示，这些表示在 WMT 的人类判断上训练；相比 n-gram 方法能提供更好的语义理解，但为了达到最佳性能需要下载模型并进行任务特定的微调）。
我在这里介绍的是最知名的指标，但所有这些指标都有变体和扩展，仅举几例：CorpusBLEU、GLEU、MAUVE、METEOR。

<HtmlEmbed src="d3-text-metrics.html" frameless />

一旦你得到每个样本的准确率分数，就可以用几种方式在整个数据集上**聚合**它。一般来说，人们会对结果取平均，但你可以根据自己的需求做更复杂的事情。（有些指标自带聚合方式，例如 CorpusBLEU。）

如果你的分数是**二值**的，就看**精确率**（当假阳性代价高昂时至关重要）、**召回率**（当漏掉阳性结果代价高昂时至关重要）、**F1**（平衡精确率与召回率，适合不平衡数据），或 **MCC**（马修斯相关系数，通过考虑混淆矩阵的所有元素，能很好地处理不平衡数据集）。
如果你的分数是**连续值**（虽然可能性较小），可以用**均方误差**（惩罚大误差，但对离群点权重很高）或**平均绝对误差**（比 MSE 更均衡）。<Sidenote> 如果你假设数据应遵循某个特定的线性回归模型（例如你在研究模型校准），可以看 **R²** 之类的度量，或 **Pearson**（用于线性关系，假设正态性）、**Spearman**（用于单调关系，不假设正态性）等相关系数。不过，这有点超出本文范围。 </Sidenote>

更一般地说，在选择指标及其聚合方式时，需要记住你的任务真正关心的是什么。在某些领域（例如医疗、面向公众交互的聊天机器人），你不想衡量平均表现，而是需要一种方式来评估你能得到的**最差表现**（输出在医疗质量上的表现、毒性等）。
<Note title="延伸阅读">
- 这篇[博客](https://ehudreiter.com/2024/07/10/challenges-in-evaluating-llms/)讨论了评测 LLM 的一些挑战。
- 如果你在找指标，也可以在[这个组织](https://huggingface.co/evaluate-metric)中找到一份很好的列表，包含描述、分数范围和使用场景。
</Note>


<Note title="使用自动化指标的优缺点">
自动化基准有以下优点：
- **一致性与可复现性**：你可以在同一个模型上把同一个自动化基准跑 10 次，会得到相同的结果（硬件差异或模型固有的随机性除外）。这意味着你可以轻松地为给定任务创建公平的模型排名。
- **以有限成本扩展规模**：它们是当前评测模型最便宜的方式之一。
- **可理解性**：大多数自动化指标都很容易理解。

不过，它们在**更复杂的任务上用途有限**：自动指标要么要求你有一个完美、唯一且无歧义的参考/标准答案，就像那些表现易于定义和评估的任务（例如毒性分类、只有一个答案的知识问答）。另一方面，更复杂的能力更难分解成一个简单而唯一的答案。
</Note>

<a id="normalization"></a>

#### 归一化

归一化是指修改一个字符串，使其符合特定的参考格式。例如，在把模型预测与参考比较时，你通常不希望因为预测中多出的空格、添加的标点或大小写而扣分。这就是你要对预测做归一化的原因。

它们对特定任务至关重要，比如数学评测——你需要从较长的预测中抽取出一个等式，再与参考比较。
在下表中，我们列出了在 MATH 数据集上使用 SymPy 朴素地从模型输出中抽取预测时遇到过的一些问题，以及特定的数学解析器 Math-Verify 是如何解决这些问题的。

| 📄 示例 |  ❗️问题 | ✅ Math-Verify | 🛑 朴素方法 |
| --- | --- | --- | --- |
| 因此，这些三角形中一个的周长是 $14 + 7\sqrt{2}$ 英寸，以最简根式形式表示。 | 抽取失败 | `7*sqrt(2) + 14` | None |
| 因此，这个无穷等比数列的和是 \(\frac{7}{9}\)。 | 抽取失败 | `7/9` | None |
| 最终答案是 $2x + 4y + z - 19 = 0$。希望这是正确的。 | 参数方程只解析了一部分 | Eq(2*x + 4*y + z - 19, 0) | 0 |
| \(23\) | 因 LaTeX 边界而抽取失败 | `23` | None |
| \((- \infty, -14) \cup (-3, \infty)\)。 | 因区间而抽取失败 | Union(Interval.open(-oo, -14), Interval.open(-3, oo)) | None |
| 100\% | 因无效符号而抽取失败 | `1` | None |
| 1/3 == 0.333333 | 不支持舍入 | True | False |
| sqrt(1/2)*7 == sqrt(0.5)*7 | 不支持数值求值 | True | False |

<Sidenote>
更多细节见[这篇博客](https://huggingface.co/blog/math_verify_leaderboard)！
</Sidenote>

归一化如果设计不当，很容易[变得不公平](https://huggingface.co/blog/open-llm-leaderboard-drop)，但总的来说，它们仍然有助于在任务层面提供信号。

它们对于评测通过思维链或推理生成的预测也很重要，因为你需要从输出中去掉推理轨迹（它不属于最终答案），才能得到真正的答案。

<a id="sampling"></a>

#### 采样

当模型生成输出时，多次采样并聚合结果，能比单次贪心生成提供更稳健的信号。
这对复杂推理任务尤其重要——模型可能通过不同路径得到正确答案。

常见的基于采样的指标有：
- **n 个样本上的 pass@k**：给定 n 个生成样本，衡量其中是否至少有 k 个通过测试。<Sidenote> 你会看到 pass@k 有两种计算方式：简单地算作 $\text{pass}@k = (c >= k)$，或用无偏估计量计算：$\text{pass}@k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$，其中 c 是 n 个总样本中正确样本的数量。 </Sidenote>

- **maj@n**（多数投票）：采样 n 次生成，取出现次数最多的答案。这有助于过滤掉偶发的输出，当模型的正确推理路径比其错误更一致时，效果尤其好。常用于数学和推理任务。
- **cot@n**（思维链采样）：采样 n 条推理轨迹并对其进行评估。可以与多数投票或 pass@k 结合使用（采样 n 条推理链，抽取最终答案，取多数或设一个阈值）。
- **avg@n**（稳定的平均分）：对 n 个样本的分数取平均。与使用“最好”或“最常见”的情况相比，这是更稳定的性能估计。

<HtmlEmbed src="d3-sampling-metrics.html" title="采样指标对比" />

使用采样评测时，务必始终报告所有采样参数（温度、top-p、k 值），因为它们会显著影响结果。

<Note title="什么时候可以用采样，什么时候不该用？">
- **用于训练评测/消融实验**：❌ 一般应避免采样指标，因为它们昂贵且会引入方差。坚持使用固定随机种子的贪心解码。
- **用于后训练评测**：✅ 采样指标能揭示贪心解码遗漏的能力（尤其是需要推理、数学或代码的更复杂任务）。
- **推理时**：✅ 这些指标有助于估计在推理时多次采样能带来多少提升。当你想研究用测试时计算能把小模型推到多远时，这尤其有用。

不过要记住，采样 k 次会把评测成本乘以 k。对于昂贵的模型或大型数据集，成本会累积得非常快！
</Note>

<a id="functional-scorers"></a>

#### 函数式评分器
函数式测试不是通过模糊字符串匹配把生成文本与参考比较，而是评估输出是否满足特定的可验证约束。这种方法非常有前景，因为它更灵活，并且允许通过基于规则的生成对测试用例进行“无限”更新（从而减少过拟合）。

**IFEval 和 IFBench** 是指令遵循评测中这种方法的绝佳例子。它们不问“这段文本是否匹配某个参考答案？”，而是问“这段文本是否满足指令中给出的格式约束？”

例如，指令可能规定：
- *“恰好包含 3 个要点”* → 验证输出中恰好有 3 个要点
- *“只把第一句的首字母大写”* → 解析并检查大小写模式
- *“至少使用两次 ‘algorithm’ 这个词”* → 统计词出现次数
- *“你的回复必须是 JSON 格式，包含键 ‘answer’ 和 ‘reasoning’”* → 校验 JSON 结构

每条约束都可以用特定的基于规则的验证器来检查，这使得这类评测比使用模型作为裁判更无歧义、更可解释、更快，而且成本低得多。

这种函数式方法对指令遵循特别有效，但要扩展到其他文本属性则需要创造力。关键在于找出文本中那些可以通过程序而非语义比较来验证的方面。

<Sidenote>
功能测试的思路来自代码评测，在代码评测中，通过单元测试做功能测试是标准做法（检查生成的代码对给定输入是否产生正确输出）。
</Sidenote>

<a id="with-humans"></a>

### 用人类
人工评测就是请人类为预测结果打分。

人工评测非常有意思，因为它具备**灵活性**（只要把你评测的东西定义得足够清楚，几乎任何东西都能拿到分数！）、**天然的未污染性**（如果由人类编写新问题来测试你的系统，这些问题有望不出现在你的训练数据里），以及**与人类偏好的良好相关性**——原因显而易见。

<Sidenote>
不过，在让人类参与评测时，你需要确保标注者足够多样，以便结果具有泛化性。
</Sidenote>

在人类参与的情况下评测模型，有几种不同的做法。

**直觉检查**（vibe-checks）指的是社区成员个人进行的手动评测，通常针对未公开的提示词，目的是获得模型在其偏好的用例上表现如何的整体“感觉”。（我也见过用“金丝雀测试”一词来指代这种做法，借用了煤矿中高信号金丝雀的比喻。）这些用例可以是最令人兴奋的，也可以是最平淡乏味的——举几个我在 Reddit 上见过的例子，涵盖德语法律问题、编程、工具使用、情色内容写作质量等。它们常被发布在论坛或社交媒体上，大多只构成轶事性证据，并且往往对确认偏误高度敏感（换句话说，人们往往会找到他们想找的东西）。

<HtmlEmbed src="d3-vibe-checks.html"/>

利用社区反馈来建立大规模的模型排名，就是我们所说的**竞技场**（arena）。一个广为人知的例子是 [LMSYS chatbot arena](https://huggingface.co/spaces/lmsys/chatbot-arena-leaderboard)，社区用户在其中与模型聊天，直到他们发现其中一个比另一个更好。投票随后被聚合成 Elo 排名（一种基于对局的排名），以此选出哪个模型“最好”。这种做法明显的问题在于主观性很高——仅凭宽泛的指南，很难让众多社区成员给出一致评分，尤其是标注者的偏好往往[受文化约束](https://arxiv.org/abs/2404.16019v1)（例如，不同的人偏好不同的讨论话题）。人们可以寄希望于投票规模之大能通过“群体智慧”效应抹平这种影响（这一效应由一位名叫高尔顿的统计学家发现，他观察到，个人为估计某个数值——比如一头猪的重量——给出的答案，可以被建模为以真实答案为中枢的概率分布）。

最后一种做法是**系统性标注**：你为付费挑选出来的标注者提供极其具体的指南，以尽可能消除主观性偏见（这是大多数数据标注公司采用的做法）。但它的成本会迅速变得极高，因为对于每一个你想评测的新模型，你都得持续地以非自动化的方式做评测；而且它仍然可能受制于人类偏见（这项[研究](https://arxiv.org/abs/2205.00501)表明，身份不同的人对模型回答毒性的评分往往差异很大）。

直觉检查是一个特别[适合你自己用例的起点](https://olshansky.substack.com/p/vibe-checks-are-all-you-need)，因为你会用与你相关的内容来测试模型。随性人工评测的优点在于成本低，并且让你能以一种基本不受限的方式利用用户的创造力，从而发现有趣的边缘情况。不过，它们也容易存在盲区。<Sidenote> 例如，科学界曾就 LLM 是否[能画](https://arxiv.org/abs/2303.12712)独角兽[有过争论](https://twitter.com/DimitrisPapail/status/1719119242186871275)。一年之后，看起来大多数模型都能画了！ </Sidenote>


一旦你想扩展到用付费标注者进行更系统的评测，你会发现主要有 3 种做法。如果**你还没有数据集**，但想探索一组能力，你给人类一个任务和评分指南（例如 *试着让这两个模型的输出都包含毒性语言；模型若输出毒性语言得 0 分，没有则得 1 分。*），并让他们能访问一个（或多个）可以交互的模型，然后请他们给出分数和理由。如果**你已经有数据集**（例如一组*你希望模型永远不要回答的提示词*，比如出于安全目的），你预先用这些提示词提示模型，然后把提示词、输出和评分指南交给人类。如果**你已经有数据集和分数**，你可以请人类通过做[错误标注](https://ehudreiter.com/2022/06/01/error-annotations-to-evaluate/)来审查你的评测方法（*它也可以用作上述类别中的评分系统*）。这是测试新评测系统非常重要的一步，但严格来说它属于评测一个评测，因此略微超出了本文的范围。

系统性人工评测的优点，尤其是在使用付费标注者时，在于你能获得**契合自己用例的高质量私有数据**（特别是当你依赖内部标注者时），而且这些数据大多是**可解释的**（模型得到的分数可以由给出分数的人类解释）。
然而，它成本更高（尤其是你很可能需要多轮标注来调整指南），而且扩展性不好。

不过总体而言，人工评测存在若干众所周知的偏见，基于第一印象、语气、与标注者价值观的一致性等，见下图。

<HtmlEmbed src="d3-human-biases.html"/>

这些偏见并不出人意料，但必须加以考虑：并非所有用例都应依赖廉价的众包标注者——任何要求事实性的任务（如写代码、评测模型知识等）都应加入另一种更稳健的评测类型来补全基准（专家、适用的自动指标等）。

<a id="with-judge-models"></a>

### 用裁判模型
为了降低人工标注者的成本，一些人开始研究用模型或衍生产物（最好是与人类偏好对齐的）来评估模型的输出。

<Sidenote>这种做法并不新鲜，2019 年就有利用[模型嵌入](https://arxiv.org/abs/1904.09675)衡量摘要质量的技术。</Sidenote>

裁判模型就是**用来评估其他神经网络输出的神经网络**。多数情况下，它们评估的是文本生成结果。

评分有两种做法：使用[通用、高能力的模型](https://arxiv.org/abs/2306.05685v4)，或使用[小型专家模型](https://arxiv.org/pdf/2405.01535)——后者专门在偏好数据上训练以做区分（可以想象成“垃圾邮件过滤器”，只不过过滤的是毒性之类的东西）。在前一种情况下，用 LLM 当裁判时，你给它一个提示词，说明如何给模型打分（例如 `Score the fluency from 0 to 5, 0 being completely un-understandable, ...`）。

模型裁判可以对复杂而细微的属性给文本打分。
例如，预测与参考答案之间的精确匹配可以让你检验模型是否预测出正确的事实或数字，但评估更开放的经验性能力（如流畅度、诗歌质量，或对输入的忠实度）需要更复杂的评估器。

它们主要用于 3 类任务：
- *为模型生成结果打分*：在给定的量表上，评估文本的某项属性（流畅度、毒性、连贯性、说服力等）。
- *成对打分*：比较一对模型输出，针对给定属性挑出更好的文本
- *计算相似度*：模型输出与参考文本之间的相似度

<Sidenote> 在本文中，我目前会聚焦于 LLM + 提示词的做法，但你绝对应该去看看分类器裁判（classifier judges）是如何工作的，因为我认为它相当稳健，且能很好地适配多种用例；也值得看看最近提出、前景可期的“以奖励模型为裁判”的做法（见[这份技术报告](https://research.nvidia.com/publication/2024-06_nemotron-4-340b)，我们[这里](https://github.com/huggingface/evaluation-guidebook/blob/main/contents/model-as-a-judge/what-about-reward-models.md)有一个小页面） </Sidenote>

<a id="pros-and-cons-of-using-judge-llms"></a>

#### 使用裁判 LLM 的优缺点
支持 LLM 裁判的人一直声称，它们能提供更好的：
- **与人类相比的客观性**：它们以客观且可复现的方式自动化经验性判断（理论上如此——在我看来，它们引入的微妙偏见超过了其价值）
- **规模与可复现性**：它们比人类标注者更具扩展性，从而能在大量数据上复现打分（前提是你控制温度）。
- **成本**：它们实例化成本低，因为不需要训练新模型，只需依赖良好的提示和一个现有的高质量 LLM。它们也比付钱给真正的人类标注者更便宜（资本主义……）。

在我看来，正确使用 LLM 裁判极其棘手，而且**在关键用例上很容易被蒙骗**：
- LLM 裁判看起来客观，但它们有许多**隐藏偏见**，而且这些偏见比人类的偏见更难察觉，因为我们不会那么主动地去寻找它们（见下文）。此外，可以通过以特定且统计上稳健的方式设计调查问题来减少人类偏见（社会学对此已研究了大约一个世纪），而 LLM 提示在这方面还不够稳健。有人把用 LLM 评测 LLM 比作制造回音室效应，会微妙地强化偏见。
- 它们确实可扩展，但会助推产生**海量数据**，而这些数据本身需要被检查以确保质量（例如，你可以通过让 LLM 裁判生成思维轨迹、或围绕其数据做推理来提升裁判质量，但这会产生更多需要分析的新人工数据）
- 它们实例化成本确实低，但在你的具体用例上，效果不如花钱请真正的专家标注者。

<HtmlEmbed src="d3-llm-biases.html"/>

因此这一节有点长，因为你需要充分了解把模型用作裁判的局限：很多人盲目地一头扎进这种做法，因为它看起来比真正与人类合作或设计新指标更省事，但最终得到的是难以解释、且带有难以剥离的棘手偏见的数据。

我个人对用模型做裁判最大的不满在于，它们会在答案选择中引入非常微妙且无法解释的偏见。我感觉，就像遗传学研究中过度杂交最终会得到功能失调的动植物一样，用 LLM 来筛选和训练 LLM，同样很可能引入细微变化，而这些变化在几代之后会产生更大的连锁反应。我认为，更小、更专用的裁判模型（例如毒性分类器）不太可能出现这类偏见，但这仍有待严格的测试与证明。

<Note title="LLM 裁判入门">
如果你想试一试，我建议先读这篇[非常好的指南](https://huggingface.co/learn/cookbook/en/llm_judge)，了解如何搭建你的第一个 LLM 裁判！

你也可以试试 [distilabel](https://distilabel.argilla.io/latest/) 库，它允许你生成合成数据并用 LLM 更新这些数据。他们有一个不错的[教程](https://distilabel.argilla.io/latest/sections/pipeline_samples/papers/ultrafeedback/)，应用了 [Ultrafeedback 论文](https://arxiv.org/abs/2310.01377)的方法论；还有一个[关于基准测试的教程](https://distilabel.argilla.io/latest/sections/pipeline_samples/examples/benchmarking_with_distilabel/)，实现了 Arena Hard 基准。
</Note>

<a id="getting-a-judge-model"></a>

#### 获取裁判模型

使用现有 LLM 时，你可以选择[通用的高能力模型](https://arxiv.org/abs/2306.05685v4)、专门在偏好数据上训练以做区分的[小型专家模型](https://arxiv.org/abs/2405.01535)，或者训练自己的模型。

**使用通用 LLM**

随着能力更强的 LLM（如 ChatGPT）出现，一些研究者开始探索用大模型当裁判。

<Note title="闭源与开源裁判模型" emoji="⚖️" variant="warning">

**闭源模型（Claude、GPT-o）的取舍：**

缺点：
- **不可复现**：模型可能通过 API 更新在毫无通知的情况下发生变化
- **黑箱**：决策过程无法解释
- **隐私风险**：数据被发送给第三方，可能泄露

优点：
- 无需本地环境或硬件要求即可轻松使用

**开源模型正在缩小差距**，同时解决了可复现性与可解释性问题。DeepSeek R1、gpt-oss 以及近期的 Qwen 模型如今都是具有竞争力的替代方案。

</Note>

如果你需要帮助挑选模型提供商，可以在[这里](https://huggingface.co/spaces/ArtificialAnalysis/LLM-Performance-Leaderboard)找到一份不错的成本分析。

**使用小型专用 LLM 裁判模型**

你也可以选择使用小型专用的 LLM 裁判。它们通常只有几十亿参数，能在大多数近期的消费级硬件上本地运行，同时可以用指令数据从零训练或微调。你通常需要遵循它们特定的提示词格式。

截至 2024 年，一些已有的模型包括 Flow-Judge-v0.1（[权重](https://huggingface.co/collections/flowaicom/flow-judge-v01-66e6af5fc3b3a128bde07dec)），38 亿参数，是在合成偏好数据集上微调的 Phi-3.5-mini-instruct；Prometheus（[权重](https://huggingface.co/prometheus-eval/prometheus-13b-v1.0)、[论文](https://arxiv.org/abs/2310.08491)），130 亿参数，是在合成偏好数据集上从零训练的模型；以及 JudgeLM（[论文](https://arxiv.org/abs/2310.17631)），70 亿到 330 亿参数，是在用多种模型生成的合成偏好数据集上从零训练的模型。现在肯定有更新的替代方案！

**训练自己的裁判**
你也可以选择训练或微调自己的 LLM 裁判。（除非你处在非常小众的领域，否则我会避免这样做。）

如果走这条路，你首先需要为感兴趣的任务收集偏好数据，这些数据可以来自
- 现有的[人类偏好数据集](https://www.kaggle.com/competitions/lmsys-chatbot-arena)
- 由模型生成的偏好数据（你可以按照上面那些小型模型裁判论文的数据部分来生成，也可以直接获取，例如从 Prometheus 的[偏好](https://huggingface.co/datasets/prometheus-eval/Preference-Collection)和[反馈](https://huggingface.co/datasets/prometheus-eval/Feedback-Collection)数据集中获取）。

然后你需要决定：是从一个小模型开始从零训练，还是从现有模型出发——你可以把它蒸馏成一个新的更小的模型，或做量化，然后用上述数据微调（如果模型很大而你的训练算力很低，可以使用 peft 或适配器权重）。

<Sidenote> 显然，[从奖励模型出发比从指令模型出发效果更好](https://x.com/dk21/status/1826292289930674590) </Sidenote>

<a id="designing-your-evaluation-prompt"></a>

#### 设计你的评测提示词

选定模型后，你需要为你的任务确定尽可能最好的提示词。

<Note title="提示词设计指南" emoji="📝" variant="info">
清楚地描述手头的任务：
- *你的任务是做 X。*
- *你会拿到 Y。*

清楚地说明评测标准，必要时给出详细的评分体系：
- *你应就属性 Z 按 1 - 5 打分，其中 1 表示……*
- *你应评估样本 Y 中是否存在属性 Z。若……则属性 Z 存在*

给出一些额外的“推理”步骤：
- *要判断这项任务，你必须先仔细阅读样本 Y 以找出……，然后……*

明确要求的输出格式（增加字段有助于保持一致性）
- *你的答案应以 JSON 给出，格式如下 \{"Score": Your score, "Reasoning": The reasoning which led you to this score\}*
</Note>

你完全可以、也应该从 [MixEval](https://github.com/huggingface/lighteval/blob/main/src/lighteval/tasks/extended/mix_eval/judge_prompts.pyy) 或 [MTBench](https://github.com/huggingface/lighteval/blob/main/src/lighteval/tasks/extended/mt_bench/judge_prompt_templates.py) 的提示词模板中汲取灵感。

<Note title="用模型做裁判时要记住的事" emoji="⚠️" variant="warning">
成对比较[与人类偏好的相关性更好](https://arxiv.org/abs/2403.16950)，优于打分，而且通常更稳健。

如果你确实想要一个分数，请使用整数刻度，并确保详细解释[每个分数代表什么](https://x.com/seungonekim/status/1749289437165769177)，或者使用加总式提示词（*回答具备这一特征得 1 分，若……再加 1 分*等）

每项能力用一个提示词来打分，往往能得到更好、更稳健的结果
</Note>

你也可以用下面这些可能更昂贵的技术来提升准确率：
- **少样本示例**：和许多其他任务一样，提供示例有助于模型推理。不过这会增加你的上下文长度。
- **参考**：如果存在参考答案，你也可以把它加进提示词，从而提高准确率
- **CoT**：[能提升较老一代模型的准确率](https://arxiv.org/abs/2212.08073)，前提是你要求模型在给出分数**之前**输出其思维链（在[这里](https://x.com/seungonekim/status/1749289437165769177)也观察到了这一点）
- **多轮分析**：可以提升[事实性错误检测](https://arxiv.org/abs/2305.13281)的效果
- 使用**评审团**（多个裁判，取它们答案的聚合）：[效果](https://arxiv.org/abs/2404.18796)优于使用单个模型。用许多较小的模型代替一个昂贵的大模型，可以显著降低成本。你也可以尝试用同一个模型配合不同的温度。
- 出乎意料的是，社区发现给提示词加上筹码（`answer correctly and you'll get a kitten`）能提升正确率。这一条效果因人而异，按需调整。

如果你在做关键任务（例如医疗领域），务必使用从人文学科移植过来的方法：1）计算标注者间一致性指标，确保评测者尽可能无偏；2）在设计评分网格时采用规范的问卷设计方法，以减轻偏见。不过，大多数人其实并不真的想要一个可复现、高质量、无偏的评测，只要能用还过得去的提示词做快速粗糙的评测，他们就满意了。（这本身没问题！只是取决于要承担的后果。）

<a id="evaluating-your-evaluator"></a>

#### 评测你的评测器

在生产环境或大规模使用 LLM 裁判之前，你需要针对自己的任务评估它的质量，确认它的分数对你确实相关且有用。

<Note>
如果你的裁判输出二分类结果，这件事会更容易，因为你可以使用可解释的分类指标（准确率/召回率/精确率）。如果它输出的是某个刻度上的分数，那么估计其与参考之间相关性的质量会困难得多。模型在刻度上做预测是出了名的差。
</Note>

因此，选定模型裁判及其提示词之后，你需要做以下几件事。

1. **选定基线**
你需要把你的评测器判断与某个基线做比较：基线可以是人工标注、另一个你确知在该任务上质量不错的裁判模型的输出、标准答案、同一模型配另一个提示词的输出，等等。

<Note title="基线重质不重量" emoji="🎯" variant="info">

你不需要很多基线样本（50 个就够了），但它们必须：
- **有代表性**：覆盖你任务的完整范围
- **有区分度**：包含边缘情况和有挑战性的例子
- **高质量**：使用你能拿到的最好的参考数据

</Note>

2. **选定指标**
你的指标将用于把裁判的评测结果与你的参考做比较。

一般来说，如果你的模型输出二分类结果或做成对比较，这个比较会容易得多，因为你可以计算准确率（成对比较），或精确率和召回率（二分类），这些指标都非常容易解释。

比较分数与人类打分或模型打分的相关性则更难。要更详细地理解原因，我建议你读这篇[关于该主题的博客章节](https://eugeneyan.com/writing/llm-evaluators/#key-considerations-before-adopting-an-llm-evaluator)。

一般来说，如果你对何时该选什么指标有点迷茫（在模型、指标等方面），也可以看看[上面同一篇博客](https://eugeneyan.com/writing/llm-evaluators/)里这张[很有意思的图](https://eugeneyan.com/assets/llm-eval-tree.jpg) ⭐。

3. **评测你的评测器**
这一步，你只需用你的模型和它的提示词去评测你的测试样本！拿到评测结果后，用上面的指标和参考为你的评测计算一个分数。

你需要决定可接受的阈值。取决于任务难度，如果你做成对比较，可以以 80% 到 95% 的准确率为目标。至于相关性（如果你用分数），文献里的人似乎对与参考的 0.8 皮尔逊相关感到满意。不过我也见过一些论文声称 0.3 就表示与人类标注者有良好相关性（^^"）所以因人而异。

<a id="tips-and-tricks"></a>

#### 技巧与提示

<Note title="缓解 LLM 裁判的已知偏见" emoji="⚠️" variant="warning">
我们在本节[引言](http://localhost:4321/#pros-and-cons-of-using-judge-llms)中讨论了 LLM 裁判的若干偏见。下面看看该如何缓解它们。

**缺乏内部一致性**：
➡️ 你可以对裁判做自一致性提示，多次提示它并保留多数输出，以此缓解

**自我偏好**：
➡️ 你可以使用评审团来缓解

**对输入扰动不敏感**：
➡️ 要求模型[在给出分数之前](https://twitter.com/seungonekim/status/1749289437165769177)解释其推理
➡️ 或者在提示词中给出连贯的评分刻度。

**位置偏见**：
➡️ 随机交换答案位置
➡️ 计算所有可能选项的对数概率，得到归一化后的答案

**冗长偏见**（或长度偏见）：
➡️ 你可以[在评分时考虑答案的长度差异](https://arxiv.org/abs/2404.04475)来缓解

**格式偏见**：
➡️ 你可以关注训练时的提示词格式（如果模型经过指令微调），并确保遵循它，以此缓解
</Note>

**为 LLM 裁判选对任务**

LLM 评测器：
- 通常**不擅长识别幻觉**，尤其是所谓部分幻觉（看起来接近标准答案，实际却略有不同）（见[这篇](https://arxiv.org/abs/2305.11747)和[这篇](https://arxiv.org/abs/2303.08896)）
- 在[摘要](https://arxiv.org/abs/2304.02554)（[这里也有](https://arxiv.org/abs/2303.16634)）、[忠实性](https://arxiv.org/abs/2307.16877)任务上与人类标注者的相关性从低到还算可以，并且在更广的[一系列任务](https://arxiv.org/abs/2406.18403)上并不总是与人类判断相关

<a id="what-about-reward-models"></a>

#### 那奖励模型呢？

奖励模型学习根据人类对给定提示词/补全对的标注来预测分数。最终目标是让它们的预测与人类偏好对齐。
训练完成后，这些模型便可用作奖励函数，作为人类判断的代理，来改进其他模型。

最常见的奖励模型类型是 Bradley-Terry 模型，它输出单一的**成对分数**，形式如下：

$$p(\text{completion b is better than completion a}) = \text{sigmoid}(\text{score}_b - \text{score}_a)$$

该模型仅使用补全之间的成对比较进行训练，这类数据比分数更容易收集，但它只能比较针对同一个提示词的若干补全，无法跨提示词比较补全。

其他模型在这一方法上做了扩展，用来预测某个补全优于另一个补全的更细致的概率（[示例](https://huggingface.co/RLHFlow/pair-preference-model-LLaMA3-8B)）。

这使得它们（理论上）能够判断补全之间的细微差异，代价是无法轻松地为同一测试集保存并比较跨提示词的众多不同分数。此外，比较过长的补全时，上下文长度和内存限制也可能成为问题。

一些奖励模型（例如 [SteerLM](https://arxiv.org/abs/2311.09528)）输出**绝对分数**，可以直接用于评测补全，无需成对比较。这类模型在评测中更易于使用，但收集数据也更难，因为在人类偏好中绝对分数往往不如成对分数稳定。

最近，也有研究提出了同时输出绝对分数和相对分数的模型，例如 [HelpSteer2-Preference](https://arxiv.org/abs/2410.01257) 和 [ArmoRM](https://arxiv.org/abs/2406.12845)。

<Note title="如何使用奖励模型进行评测？">

给定一个提示词数据集，我们可以用语言模型生成补全，并让奖励模型为其打分。

对于给出绝对分数的模型，可以把得到的分数取平均，作为合理的汇总分数。

然而，在更常见的相对分数情形下，平均奖励会被离群值（少数极好或极差的补全）带偏，因为不同提示词的奖励尺度可能天然不同（有些提示词比其他提示词难得多或容易得多）。

<Sidenote>

对于相对分数，不要直接对原始奖励取平均——离群值以及提示词难度尺度之间的差异会使结果产生偏差。应改用相对于参考结果的胜率或胜出概率。

</Sidenote>

因此，我们可以使用
- 胜率：取一组参考补全，计算模型补全中排名高于参考补全的比例。它的粒度稍细。
- 胜出概率：补全优于参考补全的平均概率，可提供更细粒度且平滑变化的信号。
</Note>

<Note title="奖励模型的优缺点">
奖励模型通常：
- **非常快**：得到分数只需要对一个相对较小的模型做一次前向传播（因为我们只得到一个分数，而不像 LLM 裁判那样得到长文本）
- **确定性**：同样的前向传播会复现同样的分数
- **不太会受位置偏见影响**：由于大多数模型只接收一个补全，顺序无法影响它们。对于成对模型，位置偏见通常也很小，只要训练数据在包含"第一个回答最优"和"第二个回答最优"两方面保持平衡。
- **无需提示工程**：因为模型会根据其训练所用的偏好数据，直接从一个或两个补全中输出分数。

另一方面，它们：
- **需要专门微调**：这一步成本可能较高，而且尽管它们从基座模型继承了许多能力，在训练分布之外的任务上仍可能表现不佳。
- **在强化学习和评测中同时使用时效率会下降**（或在训练数据与奖励模型训练数据相似的数据集上使用直接对齐算法时），因为语言模型可能过拟合奖励模型的偏好。
</Note>


<Note title="延伸阅读">
- 寻找高性能模型的好去处是 [RewardBench 排行榜](https://huggingface.co/spaces/allenai/reward-bench)。
- 你可以看看 [Nemotron](https://arxiv.org/abs/2406.11704) 论文中奖励模型是如何被使用的。
- 对于为单个提示词和补全打分的奖励模型，你可以缓存许多参考模型的分数，从而轻松看出新模型的表现。
- 在训练过程中跟踪胜率或概率（例如 [这篇](https://arxiv.org/abs/2410.11677v1) 论文所做的那样），可以帮助你发现模型退化并选择最优检查点。
</Note>

<a id="constraining-model-outputs"></a>

### 约束模型输出
在许多情况下，我们可能希望模型输出遵循非常特定格式的预测，以简化评测。

<a id="using-a-prompt"></a>

#### 使用提示词
最简单的做法是添加任务提示词，其中包含关于模型应如何作答的非常具体的指令（`Provide numerical answers in digits.`、`Use no abbreviation.` 等）。

这未必总能奏效，但对能力强的模型应该足够好。例如，我们在 [GAIA](https://huggingface.co/papers/2311.12983) 论文中采用的就是这种方法。

<a id="few-shots-and-in-context-learning"></a>

#### 少样本与上下文学习
下一种方法是通过所谓的"上下文学习"来约束模型。在提示词中提供示例（即 `few-shot prompting`），会让模型在回答实际样本时，隐含地偏向于遵循重复出现的提示词形式。

<Note>
直到 2023 年底，这种方法总体上效果都相当不错！

然而，随着指令微调方法的广泛采用，以及在模型预训练后期（持续预训练）加入指令数据，较新的模型已经偏向特定的输出格式（[这里](https://arxiv.org/abs/2407.07890)称之为*在测试任务上训练*，而我称之为*过拟合提示词格式*）。推理模型也因为推理轨迹而与少样本示例配合得不太好。

对于上下文规模较小的旧模型，这种方法也可能受限，因为有些少样本示例无法放进上下文窗口。
</Note>

<a id="structured-text-generation"></a>

#### 结构化文本生成
结构化文本生成会把输出约束为遵循给定路径，例如由语法或正则表达式定义的路径。`outlines` 库使用有限状态机实现这一点，非常巧妙。（还存在其他方法，例如在生成 JSON 时使用交错生成，但有限状态机是我最喜欢的一种。）

想进一步了解使用结构化生成时会发生什么，可以看看我们合写的[博客](https://huggingface.co/blog/evaluation-structured-outputs)：结构化生成能降低评测中的提示词方差，使结果和排名更稳定。你也可以浏览 `outlines` 的整体[博客](https://blog.dottxt.co/)，了解与结构化生成相关的有趣实现和观察。

不过，最近的一些[研究](https://arxiv.org/abs/2408.02442)似乎表明，结构化生成会把先验推离期望的概率分布太远，从而在某些任务（如推理）上降低模型表现。

<Note title="延伸阅读" emoji="📚" variant="warning">
-  ⭐ [理解使用结构化生成时的有限状态机](https://blog.dottxt.co/coalescence.html)，来自 Outlines。对他们方法如何运作的讲解非常清晰！
- [Outlines 方法的论文](https://arxiv.org/abs/2307.09702)，对上述内容的更学术化解释
- [交错生成](https://github.com/guidance-ai/guidance?tab=readme-ov-file#guidance-acceleration)，另一种为某些特定输出格式约束生成的方法
</Note>

<a id="the-forgotten-children-of-evaluation"></a>

## 评测中被遗忘的孩子

<a id="statistical-validity"></a>

### 统计有效性

在报告评测结果时，除了点估计，还必须给出**置信区间**。

这些基于原始分数的置信区间，可以通过分数的标准差或[自助法（bootstrapping）](https://en.wikipedia.org/wiki/Bootstrapping_(statistics))得到——对自动指标来说，这相对简单——对模型裁判来说，一篇[近期论文](https://arxiv.org/pdf/2511.21140)建议用估计量做偏差校正。对基于人类的评测，你应该报告一致性。

你也可以用提示词变体来计算这些区间：用略微不同的方式问同样的问题，或者用不同的提示词格式在同一批样本上重新运行。

<a id="cost-and-efficiency"></a>

### 成本与效率


在设计和报告评测结果时，我们需要开始集体报告结果与模型运行成本之间的关系！一个需要 10 分钟思考和 10K token 才能答出 10 + 1 的推理模型（因为它决定就二进制与十进制算术展开一整段跑题论述），其效率远低于一个只用少数几个 token 就答出 30 的小模型。

<img src={envImage.src} alt="模型评测的环境影响指标" style="height: auto !important; object-fit: contain !important; display: block; margin: 0 auto;" />
</div>

我们建议报告以下内容：
- **token 消耗**：报告评测期间使用的输出 token 总数。这对估计**效率**尤为重要，而且它会影响以模型作为裁判的评测的成本。token 数量直接影响金钱成本，并帮助他人估计算力需求。**金钱成本**也可以是效率的一个良好代理指标。

<Sidenote> 在比较不同评测方法时，这些成本指标也可能很关键。例如，用一个强大的 LLM 作为裁判可能比自动指标提供更好的信号，但 100 倍的成本增长可能并非对所有用例都值得。同样，基于采样的指标（pass@k、maj@n）会让成本随样本数量成倍增加，这应当与它们带来的信号提升相权衡。</Sidenote>

- **时间**：记录模型完成评测所需的推理时间。这既包括实际推理时间，也包括 API 速率限制带来的任何额外开销。这对任何对时间敏感的应用（比如 GAIA2 中的某些智能体工具使用）尤为重要。

最后但同样重要的是，考虑到地球上可用资源的整体状况，报告你所运行的模型的环境足迹正变得越来越重要。这包括训练产生的碳排放和推理时的能源消耗，而这些取决于模型规模、硬件（如果你知道的话）和生成的 token 数。一些更小或量化的模型能达到非常有意思的性能与消耗之比
