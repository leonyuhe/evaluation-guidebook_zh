<a id="reasoning-and-commonsense"></a>

#### 推理与常识

推理与常识数据集往往是“历史”数据集，构建于 BERT 和嵌入模型的时代、LLM 热潮之前。它们在当时相当有挑战性（尤其因为它们常常是针对当时的模型对抗性地构建的），但如今它们 1）太简单 2）已被污染/饱和，只应被用于消融实验或作为预训练评测。较大的数据集有时也包含错误或低质量问题，因为它们往往是通过 Amazon Mechanical Turk 构建的，以便快速、低成本地扩大规模（而如今这件事改由用 LLM 生成评测问题来完成）。

[ARC](https://arxiv.org/abs/1803.05457)（2018）（不要和 ARC-AGI 混淆）是一个基于人类测试构建的小学科学 MCQA 数据集。选项是针对当时的词共现系统对抗性地挑选的。它有几个子集，质量更高的 `challenge` 子集至今仍用于预训练。[WinoGrande]([https://arxiv.org/pdf/1907.10641](https://arxiv.org/pdf/1907.10641))（2019）是一个众包（mechanical turk + 验证）的代词消解/填空数据集，使用对抗性的成对条目来骗过模型。这两个数据集对模型来说都相当难，直到 2022 到 2023 年才被攻克。

不少历史数据集专门考察需要某种常识理解、并能与现实世界对应的推理。[HellaSwag]([https://arxiv.org/abs/1905.07830](https://arxiv.org/abs/1905.07830))（2019）要求 LLM 在一组对抗性选项中选出正确的下一句，文本来自 ActivityNet 的说明文字和 Wikihow 的教程。（它是一个名为 Swag 的数据集的后续）。由于大多数句子来自教程或活动描述，它们往往需要物理常识的支撑才能解决。同样地，[CommonsenseQA]([https://arxiv.org/abs/1811.00937](https://arxiv.org/abs/1811.00937))（2018）是一个基于 ConceptNet 构建的常识 MCQA 数据集——标注者编写问题，然后用概念上接近的干扰项作为选项。[PIQA]([https://arxiv.org/abs/1911.11641](https://arxiv.org/abs/1911.11641))（2019）专门考察物理常识问题（由 [Instructables.com](http://Instructables.com) 上的示例创建，其选项同样是通过语义扰动或改写得到的对抗性选项）。[OpenBookQA]([https://arxiv.org/abs/1809.02789](https://arxiv.org/abs/1809.02789))（2018）提供开卷事实来帮助回答 MCQA 问题——然而，这些问题还需要潜在的常识知识。

一个更新的、很酷的推理数据集是 [Zebra Logic](https://arxiv.org/abs/2502.01100)，它用逻辑谜题来测试模型的推理能力。他们的方法可以无限生成谜题，因此污染很少。

<a id="knowledge"></a>

#### 知识
知识领域最主要的评测数据集一直是 [MMLU](https://arxiv.org/abs/2009.03300)（2020）。它已进入饱和/污染状态，经过更深入的检查后，人们发现了若干问题：引用了不存在文档的不完整题目、错误的标准答案、有歧义的题目，以及所选主题中露骨的美国中心主义。因此它在 [MMLU-Redux](https://arxiv.org/abs/2406.04127)（2024）中得到了清洗，在 [**MMLU-Pro**](https://arxiv.org/abs/2406.01574)（2024，目前社区使用的主要替代品）中用更复杂的题目和更多答案进行了扩展，并针对文化偏见在 [Global-MMLU](https://arxiv.org/abs/2412.03304)（2024）中做了翻译与标注。这些主要用于预训练评测和消融实验。

对于后训练，人们会关注更难、更高质量的知识数据集。[**GPQA**](https://arxiv.org/abs/2311.12022)（2023）是生物学/化学/物理学领域的博士水平定制题目，其设计目标是让正确领域的博士生能够回答，而其他人不行。最常用的子集是 `diamond` 子集，但自 2023 年发布以来，它也开始出现污染。

最后但同样重要的是，名字起得颇为浮夸、质量却非常高的 [**Humanity's Last Exam**](https://agi.safe.ai/)（2024）收录了 2.5K 道由各领域专家众包提供的问题，横跨多个领域。它大体上是不公开的，题目既需要复杂的知识，也需要推理。它至今仍未被攻破，在我看来是个很酷的数据集。唯一的问题是，由于没有办法快速给模型打分，如今人们改用 LLM 裁判来评估模型的答案，而不是对照标准答案来检查，所以它属于那种在真实使用中会得到完全不可比结果的评测。

不过，尽管在几年前测试模型潜在知识的原始质量非常合理（在训练过程中检验模型质量时也仍然有意思：预训练阶段用 MMLU-Pro 这类评测，后训练阶段用 GPQA/HLE），我认为未来几年我们会慢慢淡出这类基准，原因有两个。

1. 它们正变得越来越难以为人类所解读：题目复杂到非专家几乎无法理解在每道题上的表现意味着什么（也难以确认数据集本身不含错误）
2. 如今模型已经接入互联网访问等工具，潜在知识评测正越来越多地变成网页搜索与检索评测，因此它们本身的意义在下降。简言之，我们正在从闭卷评测走向开卷评测。做个类比：在法国教育体系中，高中是闭卷考试，但进入大学后，通常假定你可以访问数据库和互联网，评分不再那么看重你背下了什么，而更看重你在可以自由获取信息的前提下如何推理。我相信随着模型能力提升，LLM 评测也会出现同样的变化。

<a id="math"></a>

#### 数学
数学评测数据集一直被用作推理与逻辑基准测试的代理指标，当然，它们同时也用于检验模型能否解出数学题。

两个参考级的数学评测数据集是 [GSM8K](https://arxiv.org/abs/2110.14168)（2021），包含小学水平的数学题；以及 [MATH](https://arxiv.org/abs/2103.03874)（2021），它汇集了网上的奥数题，过去几年里已经达到饱和/数据污染状态。前者后来被几个数据集扩展：[GSM1K](https://arxiv.org/abs/2405.00332)（2024）用 1K 道新题做了重制，用来检验哪些模型在前者上受到了污染；[GSM-Plus](https://arxiv.org/pdf/2402.19255) 用对抗性改动（干扰项、数值变体等）对题目做了改写；[GSM-Symbolic](https://arxiv.org/abs/2410.05229)（2024）用得较少，但很有意思，它把 GSM8K 改写成题目模板以防止污染：题目可以无限重新生成。

社区目前主要聚焦于使用以下几类：
- MATH 的后续数据集，即 [**MATH-500**](https://huggingface.co/datasets/HuggingFaceH4/MATH-500)（采样出的 500 道题的代表性子集，以避免过拟合）和 MATH-Hard（只有最难的 500 道题）
- **AIME**（[24](https://huggingface.co/datasets/HuggingFaceH4/aime_2024)、[25](https://huggingface.co/datasets/math-ai/aime25)），面向高中生的美国奥数数据集，发布时是什么样就怎么用。这些数据集有意思的地方在于，由于它们由每年更新、难度相当的题目构成，可以通过比较发布时的结果与上一年数据集上的结果来检验数据污染
- [**Math-Arena**](https://matharena.ai/)，一份持续更新的竞赛与奥数题汇编，会定期刷新（它包含 AIME25，但也包含很多其他竞赛！）

这些数据集大多其实已经不再"那么难"了，因为它们的难度止步于小学水平（尽管 GSM-Symbolic 允许生成包含更多递归层级的题目，从而在合成层面提高难度）。在另一端，[FrontierMath](https://arxiv.org/abs/2411.04872)（2024）试图提供难度高得多的数学题，由数学家为此专门逐题编写。该数据集理论上是私有的（但看起来 OpenAI 曾获取到数据集的一部分——真是遗憾）。[Humanity's Last Exam](https://agi.safe.ai/)（2025）（已在知识部分介绍过）也包含有意思的"为此次发布专门编写"的数学题，需要复杂推理（尤其是一些定理证明）。

就我个人而言，预训练评测会用 AIME25 和 MATH-500，后训练评测会用 Math-Arena。

<a id="code"></a>

#### 代码
由于智能体需要与工具交互，它们必须具备编程能力：如果它们是代码智能体，就要能直接调用工具；或者要能理解在出问题时如何调试工具输出（代码智能体和 JSON 智能体都是如此，二者的区别见[这里](https://huggingface.co/learn/agents-course/en/unit2/smolagents/tool_calling_agents)）。代码评测集也是推理能力不错的代理指标。

回顾历史，2021 年的代码评测集有 [MBPP](https://arxiv.org/abs/2108.07732)，包含 1K 道众包收集的、仅限 Python 的入门级编程题；[APPS](https://arxiv.org/abs/2105.09938)，包含 10K 道从编程面试和分享网站中筛选出的代码生成题；以及随 Codex 模型一同推出的 [HumanEval](https://arxiv.org/abs/2107.03374)，与前面两个不同，它的题目是"专为发布而编写"的，这在当时非常出色！它还附带一个沙箱，以避免在评测者机器上执行有问题的代码。（这篇论文最后还引入了 `pass@k` 的估计量，在此之前，`pass@k` 是通过字面检查在 n 次中成功次数是否超过 k 次来计算的。）


[EvalPlus](https://openreview.net/pdf?id=1qvx610Cu7)（2023）团队制作了 HumanEval+ 和 MBPP+，作为前者的扩展：增加了更多测试用例，修复了原始数据集中的 bug，并补充了更多输入。[EvoEval](https://arxiv.org/abs/2403.19114)（2024）也对 HumanEval 做了变体，对题目做语义改写并加上难度标注。

对于最终版模型，你可能需要更难或未被污染的题目。

[**LiveCodeBench**](https://arxiv.org/abs/2403.07974)（2024）沿用了类似的"从 LeetCode 类网站抓题"的做法，但它非常有意思，因为它记录了题目的日期，从而可以比较模型在训练完成之前和之后创建的题目上的表现。这是一个出色的无污染基准，我很期待它更新！

[**AiderBench**](https://aider.chat/docs/leaderboards/)（我想是 2024 年底上线的？）同样使用现有编程网站的数据（具体是 Exercism），但它不止于解题，而是专门测试代码编辑与重构。

对于后训练，你需要更整体的评测，于是有几个基准不再局限于在独立题目上评测，因为那种评测并没有考察复杂的编程能力。[RepoBench](https://arxiv.org/abs/2306.03091)（2023）测试 Python 或 Java 的仓库级自动补全系统，数据来源是 GitHub 上的代码。它的构建方式是遮蔽代码库中的随机行并要求补全，补全内容要么是跨文件函数，要么是文件内函数，并定义了几个测试层级（检索、补全，以及两者的组合）。

[**SweBench**](https://openreview.net/pdf?id=VTF8yNQM66)（2024）是这方面更知名、更完整的版本，同样使用 GitHub，但这次测试的是模型能否解决已有的 issue，因而涉及逻辑理解、跨文件编辑与执行、长上下文推理等能力。

[**CodeClash**](https://codeclash.ai/)（2025）是编程领域的竞技场（arena），模型编写的代码与其他模型的代码相互竞争、编辑并迭代。

此时，我会建议关注 LiveCodeBench、AiderBench 以及 SWE-Bench 中质量更高的子集（SWE-Bench verified），并阅读 [METR 报告](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)，了解代码助手在实际使用中的有用性。

<a id="long-context"></a>

#### 长上下文
要在长时间的讨论中与用户正确交互而不迷失线索，你需要良好的长上下文管理。（想想挺有意思：3 年前模型的最大上下文长度还是 2048 token，而如今我们大多已在 128K 及以上。）

2023 年最早开始测试这一点的评测大概要数 [NIAH](https://github.com/gkamradt/LLMTest_NeedleInAHaystack)（Needle in a Haystack，大海捞针）：把一条随机事实放进一段很长的无关文本中，要求模型把它检索出来。它提供了一个简洁的框架，用来评测模型最容易在上下文的哪个位置遗忘信息，以及从多长的上下文开始遗忘。2023 年模型在这上面表现很差，到 2025 年已接近解决。

此后出现了更复杂的长上下文扩展。[RULER](https://arxiv.org/pdf/2404.06654)（2024）加入了多跳追踪（要求模型沿变量链追踪以取得正确取值）、词频变化，并增加了 NIAH 的问答变体。它如今也接近解决。[Michelangelo](https://arxiv.org/pdf/2409.12640v2)（2024，有时也被称为 MRCR，即 multi round co reference）同样使用合成长上下文数据：任务（长度各异）测试模型能否精确复现上下文中独一无二的片段（以及判断相关信息是否存在），并理解一段文本的修改序列。它随后在 [OpenAI MRCR](https://huggingface.co/datasets/openai/mrcr)（2025）中得到扩展。[InfinityBench](https://arxiv.org/abs/2402.13718)（2024）是多语言的（英文和中文），提供 100K token 的合成数据任务，覆盖多种目标（问答、类似 NIAH 的检索、超长上下文上的计算……）。InfinityBench 仍然能提供一些信号。

[**HELMET**](https://arxiv.org/abs/2410.02694)（2024）把任务与既有基准组合起来，得到一个信号更丰富的大型单一数据集：RAG 与问答数据集（Natural questions、TriviaQA、PopQA、HotpotQA、Narrative QA 和 InfinityBench）、召回（RULER 和 JSONKV）、带引用的生成（ALCE 的子集）、摘要、段落重排（MS MARCO）、上下文学习（TREC、NLU、Banking77、CLINIC150）。基准聚合很全面，但存在重复度量的风险：比如，不要既用 HELMET 又用 InfinityBench 测你的模型，再把结果聚合起来，因为那等于把同一项评测跑了两遍！在 2025 年，它仍有足够的区分度来比较模型。

我最喜欢的长上下文评测思路是 [Novel Challenge](https://arxiv.org/abs/2406.16264)（2024）——针对过去一年出版的虚构类书籍的 1K 条真/假陈述（由这些书的读者撰写！），必须读过并理解全文才能正确作答；以及 [**Kalamang 翻译数据集**](https://arxiv.org/abs/2309.16575)（2024）——模型需要先读一本语法书，再从英文正确翻译成 Kalamang（Kalamang 是资源极稀缺的语言，网上完全没有它的资料——只有 200 名使用者）。Kalamang 翻译集显然可以扩展到其他低资源语言（不过更酷的是扩展为使用基于规则的语法检查器来检验生成的有效性，从而得到严格的准确率，而不是依赖 BLEU……）。

<a id="instruction-following"></a>

#### 指令遵循
两个主要的指令遵循数据集是 [**IFEval**](https://arxiv.org/abs/2311.07911)（2023）及其扩展 [**IFBench**](https://arxiv.org/abs/2507.02833)（2025）。在我看来，IFEval 是近几年最聪明的评测思路之一：模型被要求遵循格式指令（涉及关键词、标点、词数/句数、markdown 或 html 等文件类型格式，等等）。每一条这样的条件都能用一个特定的解析测试来检查：这意味着该评测是少有的自由形式生成式评测之一，能拿到严格分数而不依赖模型裁判。

更一般地说，它属于功能正确性/单元测试这一评测类型，这也是我个人最喜欢的模型评测方式。它也很容易重新生成或扩展，以防止数据污染。

顺带一提，有些基准也测试“非指令遵循”（不遵从）：[CoCoNot](https://www.arxiv.org/pdf/2407.12043)（2024）尤其会测试模型面对不完整（欠指定/不清晰）、无法回答（因信息缺失，或是在把 AI 拟人化，常常会诱发幻觉）、或不安全的请求时，是否会拒绝遵从。它先由人工撰写查询、再由模型撰写不遵从的请求，然后经过过滤，构建出一个以分类问题形式呈现的评测集。

<a id="tool-calling"></a>

#### 工具调用
工具的出现，是推动 LLM 迈入智能体领域的功能之一。

[**TauBench**](https://arxiv.org/pdf/2406.12045)（2024）评测模型在零售和航空领域回答用户查询的能力（下单/预订/查商品等）。数据库用合成样本模拟真实领域数据，只有当 1）模型的动作正确更新了数据库、且 2）它恰当地回答了用户时，才算正确。为了让该基准自动化，用户由 LLM 扮演，这使得该评测运行成本相当高，且容易出错。尽管有这些局限，它仍被广泛使用，尤其是因为它能很好地反映真实用例。

[ToolBench](https://arxiv.org/pdf/2305.16504)（2023）要求调用 API（OpenWeather、Cat、HomeSearch、TripBooking、GoogleSheets、WebShop、Tabletop 等）来求解数据集中的 100 个测试用例，每个用例需要 1 到 10 次工具调用。这些 API 有些是模拟的、有些是真实的，这使得该数据集容易因意外故障而出错。因此它在 [StableToolBench](https://arxiv.org/pdf/2403.07714)（2025）中被修复并扩展：后者引入通用的 VirtualAPIServer，把所有东西都模拟出来，以保证评测稳定性，但评测依赖 LLM 裁判，又引入了另一层偏见。

[**BFCL**](https://openreview.net/pdf?id=2GmDdhBdDk)（2025，但该基准实际上已有几年历史）在这一年里演进显著，当前版本包含 4 个子集：单轮（简单工具调用）、来自用户的众包真实函数调用、多轮对话（测试长上下文中的准确率以及借助工具调用回答查询），以及智能体式（网页搜索、记忆、SQL 数据交互）。它结合抽象语法树、执行响应和状态匹配（最终状态是否为期望状态）来判断调用是否正确。人们关注 v3 来专门测试工具调用，而 v4 测试网页与搜索工具的使用。

最后，随着 MCP 的出现，也涌现了一些测试面向 MCP 的工具调用的基准——但它们大多依赖模型裁判，并使用真实世界的 API，这可能因网络问题带来潜在的失败情形/可复现性缺失（看起来给网站创建者增加的负载不算大问题，因为多数被 MCP 覆盖的服务用户群足够大）。

[MCPBench](https://arxiv.org/abs/2508.20453)（2025）把 LLM 连接到实时、真实世界的 MCP 服务器（Wikipedia、HF、Reddit、Steam、arxiv……），任务需要多轮才能解决（任务为合成生成）。该评测把对工具调用有效性与成功与否的、基于规则的检查，与用来评估查询是否得到恰当回答的 LLM 裁判结合起来。

[**MCP-Universe**](https://arxiv.org/abs/2508.14704)（2025）使用了 11 个 MCP 服务器，覆盖各种现实世界主题（现实场景导航、3D 设计、网页搜索等）。这个基准有意思的地方在于，评测依赖多个严格的评估器：一个检查格式正确性，两个检查答案正确性。由于任务可以是静态的（询问不会变化的信息）或动态的（某个仓库的 GitHub star 数、天气……），在后者的情况下，答案正确性由一个依赖具体任务的、基于执行的评测框架来判断，该框架会自动从相关来源获取最新的正确答案，并将模型输出与之比较。这比依赖 LLM 裁判要清爽得多！

[**LiveMCPBench**](https://arxiv.org/abs/2508.01780)（2025）提供了一个规模庞大、可本地部署的 MCP 服务器集合，用于测试模型在区分不同工具以完成任务方面有多强。最好的模型已经达到 80%——所以我们已经接近饱和了。不过，测试模型能否在非常长的工具列表中选出合适的工具，是一个很好的用例，随着网络逐渐 mcp 化，这一点会越来越重要。


（顺便说一句，这里有一篇关于如何编写好工具的精彩[文档](https://www.anthropic.com/engineering/writing-tools-for-agents)。）

测试单项能力能提供有价值的信号，但真实场景中的助手表现来自这些能力的组合方式。一个模型可能擅长推理，但当推理必须同时与工具调用和长上下文管理结合时就会失败，因此我们需要那些要求同时编排多种能力的评测。

<a id="assistant-tasks"></a>

#### 助手任务
我认为 **助手任务**将成为开展更进阶评测的主要方式之一：解决这类任务需要多种能力的组合（长上下文、推理、工具调用……），而基准本身能在有用的真实场景设置中，提供关于特定领域表现的洞见。相比具体能力基准，它们通常也更容易（被普通大众）理解。如果基准足够通用，它们不会检查使用了哪些具体工具，而是检查最终结果是否正确，因为复杂任务允许多条通往成功的路径。

**真实场景信息检索**

[**GAIA**](https://arxiv.org/abs/2311.12983)（2023）通过要求模型组合使用工具、推理与检索来解答真实查询（有时还包含文档），开启了现代智能体评测。问题被分为 3 个级别，第一级如今已饱和，第三级对模型来说仍然困难。它也是那种你找到的数字会因评测方法而分散的基准之一，因为人们要么报告公开验证集上的结果，要么用 LLM 裁判在私有测试集上评测（公开排行榜在[这里](https://huggingface.co/spaces/gaia-benchmark/leaderboard)）。

后来 [BrowseComp](https://cdn.openai.com/pdf/5e10f4ab-d6f7-442e-9508-59515c65e35d/browsecomp.pdf)（2025）复现了这一思路，测试的是同一件事（模型能否借助工具和在线信息，为特定查询找到恰当的答案），但不保证结果的唯一性，因为问题是从结果出发反向构造的，难度各不相同：例如，要检索某篇特定论文，问题会通过组合元数据信息来构造，比如“哪篇关于 Topic 的论文发表在 Conference 上，作者中有一位 Nationality 国籍的人，另有两位来自 Entity？”不过，这个基准目前大概也更难。

[**GDPval**](https://arxiv.org/abs/2510.04374)（2025）在来自“对美国 GDP 贡献最大的行业”的 44 种职业上评测模型，使用模型裁判将模型表现与人类表现进行比较。

最后，[GAIA2](https://huggingface.co/blog/gaia2) 超越了简单的信息检索，使用一个模拟的移动端环境，测试助手能否正确回答依赖事件链与工具调用的查询。就目前而言，对模型来说最难的是时间敏感以及刻意加入噪声（模拟 API 调用失败）的子集，而搜索与执行对 SOTA 模型来说似乎极其简单。

**科学助手**

[SciCode](https://arxiv.org/abs/2407.13168)（2024）测试模型能否通过编写恰当的科学代码来解决现实中的科学问题，覆盖多个 STEM 领域（从生物学到数学、化学……）。题目取自真实工作流程，每个核心问题都被分解为更简单的子问题。第一版的评测由科学家和模型裁判完成——在论文发表时模型表现相当差（得分不足 5%），但我不确定在哪里能找到最新的结果。

[PaperBench](https://arxiv.org/abs/2504.01848)（2025）同样测试模型能否复现机器学习研究，但这次的设置更难：给定 ICML 的高质量论文，模型必须重建与之对应的代码库（论文作者贡献了 8000 个单独评分的任务，按评分标准树组织，并对最终评分加权）。该基准用 LLM 裁判评测（不过我怀疑，只要稍微约束所要求代码的形态，其中一部分可以自动完成）。

[DSBench](https://arxiv.org/pdf/2409.07703)（2025）是一个多模态数据分析基准，使用 Kaggle 与 ModelOff（金融数据）的样本。从附录中的示例看，ModelOff 的题目似乎以多项选择的形式给出，这很可能让任务更简单，而 Kaggle 的任务各自有自己的指标。

[**DABStep**](https://arxiv.org/abs/2506.23719)（2025）在以往属于私有（因而未被污染）的运营数据分析工作负载上评测模型，使用真实的提问与数据。所有题目都需要多步推理和多样化的文档解析，当然还需要特定的数据操作技能。这是一个很棒的评测，因为它很难，且复现了真正有用的真实用例；而且每道题都有标准答案，所以评测无偏且成本不高。

助手任务在贴近现实的场景中测试综合能力，但它们要么是动态且只读的，要么处于不会变化的环境之中。要评测适应性与动态决策，我们需要能够“给模型带来意外”的环境。

<a id="game-based-evaluations"></a>

#### 基于游戏的评测
**基于游戏**的基准非常有意思，原因有几个：它们通常评测对变化环境的适应能力（与大多数静态的助手任务相反），需要长上下文推理，而且最后同样重要的是，它们**易于理解**。然而，它们并不扎根于现实生活，也未必能反映在真正有用的用例上的良好表现。

其中最有名的正式评测大概是 [ARC-AGI](https://arcprize.org/arc-agi)。第一版（2019）由一系列谜题网格组成，模型必须在没有明确给出规则的情况下找出该序列的最后一项。在我看来，这个基准很像面向逻辑的智商测试，它在 2024 年几乎被解决。一个类似的基准（规则外推）是 [Baba is AI](https://arxiv.org/abs/2407.13729)（2024）。该基准的最新版本 ARC-AGI3（2025，进行中）仍在开发中，包含专门为该基准打造的全新游戏（需要探索、复杂规划、记忆管理……）。它仍在进行中，目前在已公布问题上的最佳解法是对游戏进行暴力穷举。

社区与模型提供方已经探索了一批用 LLM 玩现有游戏的做法。单人冒险类游戏/RPG，比如 [TextQuests](https://huggingface.co/blog/textquests)（2025）或 [Pokemon](https://github.com/benchflow-ai/benchflow/tree/main/libs/pokemon-gym)（2024）（例如 [Claude](https://www.twitch.tv/claudeplayspokemon) 与 [Gemini](https://www.twitch.tv/gemini_plays_pokemon) 的 Twitch 直播），要求模型把超长程规划与达成目标结合起来，而这需要恰当的长上下文记忆管理、推理和回溯能力。单人生存类游戏，比如 [Crafter](https://arxiv.org/abs/2109.06780)（2021，灵感来自 Minecraft），也需要同样的能力。已有相当数量的单人游戏环境被整合进 [Balrog](https://arxiv.org/pdf/2411.13543)（2024）基准。

竞争性诈唬类游戏，比如 [Poker](https://arxiv.org/html/2501.08328v1)（2025）、[Town of Salem](https://github.com/summersonnn/Town-Of-Salem-with-LLMs)（2025）这类黑手党变体、Werewolf（2025，见[此处](https://arxiv.org/abs/2407.13943)/[彼处](https://werewolf.foaster.ai/)），或者 [Among us](antimlabs.com/amongais
)，对于测试逻辑、推理以及欺骗能力都非常有意思。例如，Claude Opus 4 在扮演吸血鬼（欺骗性角色）时无法赢下 Town of Salem，但扮演农民（非欺骗性角色）时表现不错。合作类游戏，比如 [Hanabi](https://arxiv.org/abs/2510.04980)，也可以用来测试受限环境下的适应性与沟通能力。

这些游戏还有一个很妙的地方：它们有单一且毫不含糊的通过/失败指标——LLM 到底有没有赢下这局游戏？目前，如果我要用它们来评测模型，我大概会看 TextQuests 来测能力，看 Town of Salem 来测安全。

除了在受控环境中测试能力，人们还探索了终极的无法作弊的任务：预测未来。

<a id="forecasters"></a>

#### 预测者
过去一年里，出现了一类全新的、无法被污染的任务：预测。（我猜严格来说，股票市场预测可以通过某些操纵来作弊，但希望我们还没走到有财务动机去搞坏评测的那一步。）它们应当要求模型跨多个来源推理，以尝试解答尚未发生的事件相关问题，但这些基准是否有足够的区分度、能带来足够强的价值，目前并不确定；而且它们很可能强化 LLM 那种“老虎机式成功”的感觉。（模型在某些事件上的表现接近随机，是因为这些事件本就无法预测，还是因为模型不擅长？反过来，如果模型能正确预测某个事件，是这个问题太简单，还是太套路化？）

[FutureBench](https://huggingface.co/blog/futurebench) 测试模型能否预测未来会登上新闻的事件。它使用两类来源：浏览网页，以及由 LLM 生成、时间跨度为每周的问题；再加上来自博彩市场的用户预测。所有数据在使用前都会经过大量过滤与清洗。目前，在人类创建的赌注上，模型仅比随机略好；在模型生成的问题上，成功率约为 3/4（这些问题很可能更容易）。

[FutureX](https://arxiv.org/abs/2508.11987) 与之类似，但使用的是一组特定网站（预测市场、政府网站、通用排名网站和实时数据平台），然后用模板生成关于潜在未来事件的问题（`when will STOCK reach POINT?`）。每天生成 500 个问题，并会过滤掉意外不相关的问题。

[Arbitrage](https://arxiv.org/pdf/2412.18544) 中生成问题也采用了类似思路，核心差别在于时间跨度：那里的问题应当到 2028 年才会揭晓结果。

顺着相似的路子，你还会看到一些竞技场：给 LLM 提供资金，让它们主动在金融市场上交易（比如 Alpha Arena 或 Trading Agents）——这类实验不太可能给出有意义的结果，因为受成本所限，它们往往每个模型只跑一次，于是你无法获得任何统计显著性。

<a id="recommendations"></a>

#### 建议

<Note title="TLDR" emoji="🎯" variant="info">
随着能力的一次次跃升，评测的格局也在演变：从测试孤立技能，转向在更贴近现实的场景中衡量综合表现。

截至 2025 年 11 月，我推荐使用：

- **核心能力**（面向模型构建者）：训练阶段仍然用旧的能力评测；后训练阶段用 AIME26（等它发布后）、GPQA、IFEval、SWE-Bench，以及一个你自己选择的长程评测，比如 HELMET、TauBench，或者如果你面向工具使用，就用 BFCL
- **核心能力**（用于推理阶段比较模型）：IFBench、HLE、MathArena、AiderBench 和 LiveCodeBench、MCP-Universe
- **长程任务**（衡量真实世界表现）：GAIA2、DABStep、SciCode，或针对你的用例做领域特定评测
- **游戏**（为衡量鲁棒性与适应性增添一点乐趣）：ARC-AGI3（等它发布后）、TextQuests、如果你关心安全就用 Town of Salem，或者任何你喜欢的、能超越 Poker/Chess/Go 的游戏。

这个领域正朝着测试能力编排、而非孤立技能的评测方向走，目的是贴近实际使用。这与我们构建“好用”模型的目标一致——所谓好用，就是能可靠地把核心能力、工具使用与良好的编排结合起来解决实际问题的系统。

<Sidenote>
我希望这个领域能更重视函数式测试，而不是模型裁判；同时更重视普通人也能看懂的数据集与任务。
</Sidenote>
</Note>

如果你想探索更多数据集，可以在[这里](https://github.com/huggingface/evaluation-guidebook/blob/main/contents/automated-benchmarks/some-evaluation-datasets.md)找到一大串较早的有趣基准，以及我的笔记。
</Note>
