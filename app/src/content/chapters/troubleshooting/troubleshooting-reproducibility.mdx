假设你读了一份关于某个很酷的新模型的近期技术报告，想在自己的机器上复现他们的结果……却怎么也复现不出来？
我们来探究一下原因。

<a id="different-code-base"></a>

#### 不同的代码库
要把评测分数复现到小数点后几位，你首先需要确保自己使用的代码库与你想复现的论文所用的代码库完全一致。

通常，这意味着要么使用作者提供的评测默认代码，要么使用参考库中的标准实现，比如 Eleuther 的 AI `lm_eval` 或 HuggingFace 的 `lighteval`。然而，如果没有提供评测的代码来源，那我只能为你感到遗憾——你不太可能精确复现这些结果。

如果你想轻松了解使用不同实现时会出现什么样的差异，可以看看我们与 HuggingFace 评测团队合写的[这篇博客](https://huggingface.co/blog/open-llm-leaderboard-mmlu)（⭐）。它研究了我们观察到的 MMLU 评测的 3 种常见实现（`lm_eval`、`helm` 以及原作者实现）之间的差异，以及它们如何改变模型分数。

<a id="subtle-implementation-or-loading-difference"></a>

#### 细微的实现或加载差异
我们观察到，以下这些事情很容易出错，即便使用的是同一个代码库：
- **不同的随机种子。**
	- 通常，推理受随机种子的影响比训练小。不过，它们仍会影响某些 CUDA 操作（参见 PyTorch 关于[可复现性](https://pytorch.org/docs/stable/notes/randomness.html)的页面），并且如果你使用非贪心的生成策略，还会改变预测结果。如果你使用少样本示例，它们也可能影响提示词，以及一些前处理或后处理函数。
	  -> 微小的改动就可能带来几个点的差异。
- **实际上是不同的指标**。
  即使名称相同，指标在实践中也可能不同。一些例子：
	- 如果原始实现是基于*对数似然*的 `exact match`（计算不同可能答案的对数概率），而你使用的是*生成式*的 `exact match`（只把主要的贪心生成结果与参考进行比较），你得到的分数就不会相同。
	- 我们还在一些评测代码库中看到，许多任务被定义为 `exact match`，实际上是 `prefix exact match`（只比较生成结果的开头与参考）、`suffix exact match`（恰好相反）或 `quasi exact match`（带归一化的精确匹配）。
	 -> 因此，你不能只依赖指标名称来判断发生了什么，而需要查看代码。
- **不同的归一化**。
	- 回到我们上面 `exact match` 比较的例子，在 `lm_eval` v1 中，许多任务被简单命名为生成式 `exact match`：你会由此以为预测是*照原样*与参考进行比较的。
	  但查看代码会发现，预测在与参考比较之前要先经过一步归一化（去除标点、统一数字格式等）。这显然会大幅改变结果。
	  （`lm_eval` v2 现在在大多数指标名称中包含了归一化名称。）
	 -> 这是最容易搞错的事情之一，尤其是对那些需要大量归一化/答案后处理的任务，比如数学评测（你需要从生成的解释中抽取答案）。

<Note title="模型加载影响可复现性" emoji="🔧" variant="warning">

**即使代码相同，也有四个因素会改变结果：**

- **硬件**：PyTorch 不保证在不同 GPU/硬件上可复现
- **推理库**：截至 2025 年，transformers、vllm 和 sglang 对批处理和矩阵运算的处理略有不同
- **批大小**：不同批大小 = 不同结果（为了保证可复现性，你应当固定批大小，但要小心 OOM 错误）
- **加载精度**：更低的精度（尤其是量化模型与浮点模型相比）会改变数值结果

</Note>

<a id="different-prompt"></a>

#### 不同的提示词
提示词的变化可能涉及 3 个主要方面。

**提示词本身**

你用于提示词的格式可能而且确实会大幅改变分数。

例如，对于多项选择问题，常见格式包括非常简单的变体（例如用 `A`、`A.`、`A)` 来引出选项），这些变体虽然**语义等价**（内容完全相同），却仍可能导致*同一模型出现好几个点的差异*。

<Note title="提示词格式敏感性" emoji="📝" variant="danger">

我们对此做了一些实验（在语义等价的提示词上，同一模型最多可看到 7 个点的差异，即最右侧的 5 列），并且一篇[论文观察到了类似的结果](https://arxiv.org/abs/2310.11324)。

**另一个例子**：Llama 3.1 模型能给出正确的 MATH-Hard 答案，但在 Open LLM Leaderboard 上得分很低，因为它们过拟合了 GSM8K 的提示词格式，无法适应这次评测的新格式，尽管该格式已通过少样本示例提供。

*在 MMLU 子集上的评测，acc_norm 分数（seed 0），5-shot。*

<HtmlEmbed frameless src="d3-mmlu-heatmap.html" />

这篇[出色的论文](https://arxiv.org/abs/2407.07890)⭐ 也指出了这一点的一个副作用：现在有许多模型被训练成过拟合基准的提示词和答案格式，代价是在评测时对其他提示词的适应能力。
</Note>

有些任务还会在前面加上任务提示词（例如 `The following questions are about <topic>`）——它存在与否同样会影响分数。

**系统提示词与对话模板**

对话模型通常经历过指令/偏好训练或微调。在这一阶段，它们学会了在推理时遵循特定的模板。例如，模板可能要求对话轮次以一段通用提示词（称为 `system prompt`）开头，并带有特定 token 作为前缀（通常是 `System: `）。该提示词用于为模型提供高层指令，例如人设的内容，或通用的回答风格指令。对话轮次还可能要求在文本中加入前缀关键词，例如用 `User` 表示提问、用 `Assistant` 表示回答。

使用少样本时，你还需要选择示例是以多轮形式提供（模拟用户/助手轮次），还是一次性提供（放在单个用户提示词中）。

在推理时不遵循模型期望的对话模板会严重损害其表现，因为这会把它输出推到其收敛所在的概率空间之外。

同样，如果你使用的是推理模型，需要确认你比较的是开启还是未开启思考模式的结果。

**少样本示例**

少样本示例有两件事容易搞错：少样本示例的数量、你使用的是哪些示例，以及它们的具体顺序。

<Sidenote>
使用相同的示例之所以重要，并不太令人意外——前提是我们假设某些样本比其他样本更能表达任务。也许更令人意外的是：你不仅需要使用完全相同的样本，还必须以**完全相同的顺序**呈现它们。在相同样本上改变顺序，让我们在 MMLU 的某些子集上观察到最多 3 个点的差异（你可以在[这里看到一些结果](https://huggingface.co/blog/evaluation-structured-outputs)，是第三个颜色网格图）
</Sidenote>

这也是需要关注随机种子的地方。

**参数**

对于生成式评测，需要关注的参数是确保你：1）使用**相同的句子结束 token**（对于对话模型和推理模型，你大概不应使用默认的那个）；2）允许模型在评测中**生成相同数量的 token**（这对推理模型尤其关键，它们在思考模式下需要大量 token）；3）如果使用采样，确保使用**相同的随机种子/温度参数**。
